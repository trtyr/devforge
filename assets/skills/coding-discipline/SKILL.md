# 工程纪律（coding-discipline）

> 唯一事实源：写代码方与审代码方读**同一份**纪律。纪律只有这一份，提示词里只放引用，不复述。
> 每条四要素：**触发时机 / 规则 / 反例 / 证据形态**——「什么时候用」「怎么判」「什么算错」「拿什么交差」。

## 0 · 怎么用这份纪律

1. 动手前读一遍触发时机，命中哪几条就按哪几条做；
2. 提交前**逐条**自检，把命中条目的结论写进当轮证据（见「先证后报」的证据形态）；
3. 审代码的一方拿同 12 条对照被审方的 diff 与证据，缺证据 = 没做。

纪律与既有规程冲突时：**白名单内、可逆的小决策自决并留痕；越界、不可逆、或与计划冲突才问**（plan 偏差协议优先）。

## 1 · 行为断言（上游 principle-test-behavior-not-implementation）

- **触发时机**：新增或修改任何断言（单测、集成测试、契约检查）时。
- **规则**：断言必须钉住**对外可观察的行为**，且**两头都成立**——① 换个错实现它会红（能失败）；② 只做内部重构、对外行为不变时它仍然绿（不过拟合实现）。只断言状态字段、只断言「不报错」、只断言内部调用次数 = 无效断言。
- **反例**：用 `assert!(result.is_ok())` 覆盖一个本该校验返回值的函数；断言私有函数被调用了 3 次；断言 `element.isVisible()` 却不检查它是否在视口内。
- **证据形态**：每条关键断言旁注一句「错实现形态」——把它换成哪种错实现会红；写不出这种形态的断言，当场删掉或重写。

## 2 · 先证后报（上游 principle-prove-it-works）

- **触发时机**：声称「改好了 / 跑通了 / 修完了」之前的每一次汇报。
- **规则**：先跑出事实，再报结论。汇报必须带三件套：**命令原文 + 真实退出码 + 输出摘要**。没跑过 = 不许说「应该没问题」。
- **反例**：写「测试应该都过了」而没跑；跑的是 `./run.sh` 却报成 `cargo test` 的结果；退出码非 0 却报「通过」。
- **证据形态**：命令原文（可直接复制执行）+ 退出码 + 关键输出摘要，落成可被第三方复核的证据文件（文件名与路径写清楚）。

## 3 · 减法优先（上游 principle-subtract-before-you-add）

- **触发时机**：引入新能力、新抽象、新依赖、新配置项之前。
- **规则**：先问「删掉什么能同样成立」。能靠减法（删分支、删字段、删依赖、删配置）解决的，不许用加法（新增一层、新增一个开关）解决。
- **反例**：为「以后可能要」加一个 feature flag；为一个只被一处调用的函数建一整个抽象层；为了绕过旧代码而复制一份。
- **证据形态**：本次改动里「被删掉的行/被去掉的分支」清单（哪怕为空，也要写明「已检查，无需减法」）。

## 4 · 最小 diff（上游 principle-laziness-protocol）

- **触发时机**：每一次提交之前。
- **规则**：diff 里每一行都要能对上任务本身。顺手改名、顺手格式化、顺手删「看起来没用」的代码 = 越权；无关的行留在本轮 = 污染 review。修 A 不动 B。
- **反例**：在功能改动里重排整个文件的 import；把别人的 TODO 顺手删掉；把日志级别全局调一遍。
- **证据形态**：改动文件清单 + 每个文件一行的「为什么改」；无关改动当场回退。

## 5 · 根因优先（上游 principle-fix-root-causes）

- **触发时机**：发现一个缺陷（测试红、行为不对）时。
- **规则**：先定位根因再改。症状层打补丁（加特判、加延时、加 try/catch 吞掉）只在根因确实不可改时才允许，且必须写明为什么不能改根因。
- **反例**：空指针就在调用点加 `if x.is_some()`；竞态就加锁把整个函数锁住；解析失败就返回默认值把问题藏起来。
- **证据形态**：根因定位结论（哪一行/哪个状态导致失败）+ 改动如何对应到该根因（引用具体 path:line）。

## 6 · 边界收口（上游 principle-boundary-discipline）

- **触发时机**：函数/模块的入参、返回值、错误路径、对外副作用变动的每一次改动。
- **规则**：边界一次定清：谁负责什么、错误从哪出、状态改在哪一层。跨层偷偷改状态、让调用方猜语义、把错误吞成默认值 = 破边界。
- **反例**：在业务层直接写全局状态；库函数返回 `Option` 却不说明 `None` 是什么意思；错误类型在层间层层转换后丢掉根因。
- **证据形态**：改动后的接口契约说明（入参 / 返回 / 错误 / 副作用），标出与改动前后的差异。

## 7 · 类型纪律（上游 principle-type-system-discipline，并入 principle-foundational-thinking）

- **触发时机**：定义数据结构、函数签名、状态取值时。
- **规则**：让类型承担约束——用枚举/新类型表达「只能是这几样的状态」，用类型表达「这个东西还没有」（而不是 `null` + 注释）；非法状态在编译期或入口处就被拒。
- **反例**：到处 `String` 传 id；用 `0` / `""` / `-1` 当「没有」；布尔参数控制两条不同流程（`process(x, true)`）。
- **证据形态**：新增/改动的类型清单 + 每个类型承担的约束说明。

## 8 · 读者负担（上游 principle-minimize-reader-load）

- **触发时机**：写注释、写文档、写提交信息、写函数名时。
- **规则**：读者要多想一步才能懂的地方，就多写一句；已经一眼能懂的地方，不要复述代码。一条规则只写一处，别在三处各写一遍互相漂移。
- **反例**：注释把代码逐行翻译一遍；同一约定在注释、文档、提示词里三份措辞；关键约束只存在于某个人的脑子里。
- **证据形态**：新增说明的落点清单（哪份文件哪一节），以及「本轮没有新增说明」时的显式声明。

## 9 · 上下文守护（上游 principle-guard-the-context-window）

- **触发时机**：长任务里每完成一个阶段、每次把结论交出去之前。
- **规则**：把结论沉淀成落盘文件（而不是留在对话里）；每轮只带必要的上下文进上下文窗口；引用结论时给 `path:line` 而不是复述全文。
- **反例**：把 500 行日志整段贴进回复；结论只写在聊天里、下一轮又要重讲；每次从零重新勘察已知事实。
- **证据形态**：本轮沉淀的文件路径清单 + 每个文件一句结论（其余内容靠路径引用）。

## 10 · 不阻塞人类（上游 principle-never-block-on-the-human，限定版）

- **触发时机**：遇到需要在「等一个人回答」和「先继续做」之间选择的时刻。
- **规则**：白名单内、可逆的小决策自决并留痕（写清「做了什么、为什么、怎么回退」）；越界、不可逆、或与计划冲突时才问。**问要一次问全**（带上你的发现、你的建议、可选项），不许挤牙膏式追问。
- **反例**：为一个可回滚的命名风格去问人；先问一半、拿到答案又问下一个；不问也不留痕就自己定了大方向。
- **证据形态**：自决项清单（决定 + 理由 + 回退方式）；提问项清单（问题 + 建议选项 + 阻塞点）。

## 11 · 可验证单元（上游 principle-sequence-verifiable-units）

- **触发时机**：把一个任务拆成多步执行的每一步。
- **规则**：每一步都要能独立验证：跑得起来、有明确的「做完没有」的判据。步骤之间不留「中间态」——不做完上一步就不许开始下一步。
- **反例**：把「重构 + 加功能 + 改文档」塞成一步；中间步骤没有可跑的验证；最后才发现第一步就搭错了。
- **证据形态**：步骤清单，每步带「怎么验」（命令 + 判据）与「这一步的证据在哪」。

## 12 · 幂等收敛（上游 principle-make-operations-idempotent）

- **触发时机**：任何会写文件、发请求、改状态的重复性操作（重试、续跑、批量处理）。
- **规则**：同一个操作跑两次，结果必须与跑一次相同（或明确收敛到同一状态）。重试不许叠加副作用；状态文件要能被覆盖写而不是追加成第二份真相。
- **反例**：重试时再追加一条记录；续跑把上一轮的残留证据当本轮结果；同一命令跑两遍产生两份产物。
- **证据形态**：重复执行的验证结论（跑两次的前后状态对比，或说明为何天然幂等）。

## 二 · 未纳入的原则（与理由）

以下 pstack 原则本次**不**进纪律，避免与 devforge 既有规程打架或越界：

- `principle-build-the-lever` / `principle-encode-lessons-in-structure` —— 机械门体系已承担（`devforge doc-lint` + change 路径的机械门）；本次变更本身就是「把教训编码进结构」的一次应用，不另立条目。
- `principle-explain-the-number`（性能数字）、`principle-experience-first`、`principle-exhaust-the-design-space`、`principle-redesign-from-first-principles`、`principle-outcome-oriented-execution` —— 属规划/产品/性能决策，不在写代码的纪律范围内。
- `principle-foundational-thinking`（数据结构先行）—— 并入「类型纪律」。
- `principle-model-the-domain` —— 与「类型纪律」重叠，且既有提示词已含「架构 AI-friendly / 模块边界」条款。
- `principle-migrate-callers-then-delete-legacy-apis` —— 本仓无外部兼容包袱，改 API 直接改；不单列。
- `principle-separate-before-serializing-shared-state` —— 本仓已按「每个 Agent 独占自己的产物」设计；不单列。
- `principle-attack-the-premise` —— 本仓的审查打回是零校验自动重审，没有「前提」概念；等出现「同一原因连续打回」再提炼。
