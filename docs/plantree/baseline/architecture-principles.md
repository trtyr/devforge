# Architecture Principles — 基础架构三原则

项目级约束：所有阶段、所有模块的实现都必须遵守。各 plan 落地时引用本文件，不复制内容。

## 1. 完整的错误处理系统

- Rust 侧禁止 `unwrap()`/`expect()` 滥用：只允许在「不可能失败」的场合使用并注释原因，可失败处一律 `Result` 传播
- 错误必须带上下文（哪个 Agent、哪个阶段、哪条 RPC 命令失败），用 `thiserror`/`anyhow` 类惯用法（T006 时定版）
- 可恢复与不可恢复分明：子 Agent 崩溃 ≠ 编排器崩溃；单 Agent 失败要能被编排器捕获、记录、决策（重试/终止/上报），而不是连带整个流水线
- 对外错误信息面向人和 AI 双读者：说清「发生了什么、影响什么、下一步」

## 2. 完整的日志系统

- 结构化日志（tracing 类方案，T006 定版），不是散落 println
- 按 Agent / 阶段 / 轮次打标：一次编排全程（spawn → 交互 → review 轮次 → 终止）可凭一个 run-id 串起来
- 关键事件全记录：进程 spawn/退出、RPC 命令收发、`agent_settled`、状态机迁移、review verdict
- 日志落盘到系统目录（`~/.devforge/logs/`，与 plans/profiles 同层），可配置级别；stderr 只留人类现场输出

## 3. AI Friendly 架构

devforge 自己是 AI 编排平台，其自身的产物也必须让 AI（和人类）易读易接管：

- 所有状态可查询：状态机当前态、各 Agent 存活状态、review 轮次——有明确的结构化出口（命令/文件），不是藏在一个黑盒进程里
- 产物结构化：review 问题清单、plan tree、错误报告——机器可解析优先，人可读不牺牲
- 语义清晰：模块边界、命名、协议与 plantree 文档对齐，让接手的 AI agent 靠读文档+代码就能恢复全貌
- 无魔法：行为可预测、可复现、可单独调试（单个 Agent 可脱离编排器手动起停）

## 4. 全链路可观测（DAG 流程视图）

用户拍板（2026-10-16）：流程对用户**完全透明**——用户能看到背后到底在干啥，不是黑盒。

- **图模型**：编排流程以图结构建模（DAG/流程图风格）。节点 = Agent 实例及其生命周期（spawn → 运行 → 暂停/死亡），边 = 流转（阶段推进、review 回边）。注：review 循环在图上是循环边，数据模型按有向图设计，不为了「无环」砍真实流程
- **节点可下钻**：每个 Agent 节点点开能看到它的完整运行数据——日志、think 过程、工具调用、token 消耗、RPC 事件流
- **流转可见**：流程走到哪、卡在哪、谁活着谁死了，实时可见
- **数据来源现成**：RPC 模式的事件流（text/think/tool 事件）+ 结构化日志（原则 §2）就是原料，编排器负责汇聚落盘；MVP 先做数据层（事件落盘按 run-id/节点组织），可视化宿主 = 前端（经 P003 API 消费）后续迭代

## 5. Agent 完全解耦

用户拍板（2026-10-16）：任何两个 Agent 之间零直接依赖——Plan Agent 与 Plan Review Agent 完全解耦，未来所有 Agent 同样完全解耦。

- **通信解耦**：Agent 之间永不直接对话，一切消息经编排器中转。极致形式：**Agent 的世界观里只有它自己和它的任务**——Plan Agent 收到的就是「修订意见」，不知道背后有 Review 存在；提示词因此可以完全自洽
- **数据解耦**：Agent 间只通过落盘产物交换信息（plan tree、问题清单），不共享内存/会话/状态
- **生命周期解耦**：各自独立 spawn/暂停/杀死，一个 Agent 的死亡不连坐另一个（Review 每轮用完即死就是范例）
- **配置解耦**：独立 profile，可独立替换（换模型/换提示词/重渲染）不影响其他 Agent
- **扩展解耦**：新增 Agent = 新 profile + 编排图加节点，零改动已有 Agent

后果：Agent 之间的一切协作语义都由编排器（剧本）承载——Agent 只管自己那一段，剧本才是全局知识的唯一持有者。

## 6. 厚 Agent、薄编排（插件优先）

用户拍板（2026-10-16）：智能与判断力尽量在 Agent 内部解决；Agent 之间的系统编排通道尽可能轻量——必须存在或收益大时，也要保持轻量。

- **能力下沉**：判断类逻辑（如「Agent 完没完成」）属于 Agent 内部的事，通过给 pi 写专属插件增强它的能力，让它更好地与系统对接——而不是在编排层加逻辑
- **修改系统的默认路径**：觉得哪里不好要改时，首选写/改 pi 插件增强 Agent，其次才是动编排器；编排器只做最薄的生命周期管理与通道
- **与 §5 的关系**：§5 管 Agent 间解耦，本条管能力厚薄分配——两边合起来：Agent 厚而独立，通道薄而稳定
- **示例**：完成信号——MVP 用文本标记（最简通道），演进方向 = devforge 对接插件在协议层直接发结构化信号，通道不变厚

## 落地锚点

- 错误处理与日志的具体方案（2026-10-16 定版，task-1）：
  - **错误处理**：库层 `thiserror` 枚举（`DevforgeError`，Agent/System/Config/Store 分类对应可恢复/不可恢复分明）+ `Context::ctx` 上下文扩展 + 应用层 `anyhow`
  - **结构化日志**：`tracing` + `tracing-subscriber`——JSON 层写 `~/.devforge/logs/<component>.log.jsonl`，stderr 人类层；`RUST_LOG` 过滤默认 `info`；结构化字段强制带 `component` / `run_id`
  - **基建**：tokio（异步运行时）· serde/serde_json（RPC JSONL 与配置）· uuid（run-id）
- 三原则进 P001 验收标准：骨架落地时必须有错误处理与结构化日志，不允许「先跑通再补」
