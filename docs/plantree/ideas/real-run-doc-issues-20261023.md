## DR-1 ·（致命）doc-agent 首个 prompt 静默挂死：host profile 无凭据 + 引擎对失败响应无限等待

- **真根因（10-23 晚探针矩阵定位，推翻早前「裸 pi REPL」误诊）**：
  1. host manifest 无 `api_key` 字段 → 渲染出的 9 个 profile 均无 auth.json → 模型调用必败（`No API key found`）；
  2. pi 的错误路径只回 `success:false` 的 response、**永不发 agent_settled** → 引擎 wait_settled 无限等待 → run 无声挂死；
  3. e2e 一直绿是因为 e2e 家 manifest 带 key——host 侧从未被真实调用验证过（DR-6 的直接代价）。
- **勘误**：早前 ps 观测到的「裸 pi 无参数」是 node `process.title` 覆写 argv 区的显示假象——
  探针对照实验证明带全参数的 pi 在 ps 里同样只显示 `pi`。spawn 参数路径无罪。
- **证据链**：探针1（doc profile 无 key）→ 90s 零响应零会话零网络；探针2（coding profile 无 key）→
  立回 `No API key found for the selected model`；探针3（doc profile 补 auth.json）→ `success:true, disposition:started` + 会话文件落盘。
- **修复（四层）**：
  1. ops：9 个 host profile 补 auth.json（600 权限，e2e 验证过的 key）；
  2. data：host manifest 注入 api_key（未来重渲染不再丢凭据）；
  3. code（src/config/render.rs）：渲染时 api_key 缺失当场 WARN（profile.render_without_api_key）；
  4. code（src/engine/client.rs）：wait_settled/wait_settled_with_ui 遇 `success:false` 快速失败
     （agent.command_failed WARN + 结构化错误带角色名与详情），不再傻等 settled；+1 守卫单测
     `failed_response_fails_fast_without_waiting_for_settled`（常驻假 pi 下 <4s 返回）。
- **验收**：探针3 已过；冷启动冒烟见 task-5 重跑；错误路径单测绿。

## DR-2 ·（高）引擎日志黑盒：看不到目标 agent 在干什么

- **现象**：用户原话「日志系统有大问题，不能看到目标 agent 在干啥吗？」
- **现状**：引擎只记里程碑事件（run 开始 / gate.* / agent.turn_end / phase.change）。agent 内部（正在跑哪个单元、第几轮、模型有没有回话）完全不可见，只能靠会话文件旁证——而 DR-1 场景下会话文件都不存在，等于黑上加盖。
- **修法方向**：
  - agent 生命周期事件补齐：rpc 连接建立 / 每轮请求发出（带单元 id + 轮次号）/ 每轮响应回来 / rpc 断开；
  - 或者至少把 stderr 伴读线程的产出常态化进结构化日志（P8-ISSUE-08 已铺管道，但本轮 agent 静默时日志里一个字都没有——判断是 pi 在 REPL 模式不吐 stderr）。
- **验收**：DR-1 复现场景下，日志能直接看出「agent 没被正确拉起」而不是「在慢慢写」。

## DR-3 ·（高）心跳与 run 状态只证明服务端线程活着，不证明 agent 活着

- **现象**：heartbeat 每 300ms 刷新、run status=Running，但实际工作进程是闲置 REPL。心跳的语义是「watchdog 线程活着」，不是「活儿在推进」。
- **修法方向**：心跳 payload 增加 agent 活性字段（session 文件 mtime / 最近 rpc 往返时延 / 已完成轮次计数），或在 API run 详情里透出「最后一个 agent 事件距今 N 分钟」；超阈值（如 15 分钟无任何 agent 事件）打 WARN 日志。
- **验收**：DR-1 复现场景下，心跳/日志在 ~15 分钟内主动报警，而不是靠人巡检 ps。

## DR-4 ·（中）零产出无早期预警

#### ④批量写 · 实施细则（10-23 21:27 用户拍板）

**三形态对照**：

| 形态 | 节奏 | 适用 | 病 |
|---|---|---|---|
| 两阶段（原样） | 全读→全写 | 小单元 | 大单元上下文炸（om.observations.dropped 实证）、零抗崩溃 |
| 严格穿插（DR-11 字面） | 读A→写A→读B→写B | 滞后最小/抗崩溃最好 | 步数最多（2N）、兄弟文档盲写 |
| **分组批量（采纳）** | 读A→同回合批量写A的文档组→读B→… | 大单元 | 需预算护栏 |

**自适应规则**：批量的边界画在**源文件**上（天然无内部依赖组），不画在单元上；穿插是节奏，批量是
每节奏里的写法，二者不冲突。单元 ≤6 源文件 → 整体读+1-2 个大批量回合（两阶段在小规模退化安全）；
大单元 → 形态三，枢纽文档永远压轴。

**输出预算护栏（DR-13 血换的）**：单回合所有写入总量 ≤30K tokens，超限拆回合——宁可多一趟，
不可写半截（业界实证：OpenCode #600 / PantheonOS #55 均在修大文件写入截断）。
同回合多 write 只允许不相交路径（pi 并行工具调用原生支持，平台文档确认）。

**验收**：单元回合步数 209→≤60（事件流可数）；lint/审查通过率不回退。

  Anthropic 多 agent 研究系统（边探索边把发现写文件，外部化记忆）；共识 = 外部化记忆 > 上下文硬撑。
- **改造设计**（doc contract / kickoff 工作流层，非引擎层）：
  1. **按文件粒度穿插**：读完一个源文件 → 立即产出其对应文档 → 下一个（产出结构本来就是
     文件↔文档一映射，天然支持）；
  2. **单元级枢纽（index/runbook/overview）最后写**——依赖叶子知识，顺序天然正确；
  3. 穿插中发现的跨文件问题随手记入草稿笔记（单元目录内 scratch），收尾时汇总消化；
  4. 附带收益：崩溃/中断后已完成文件的文档留存，resume 重做范围缩小（与 resume 口径案协同）。
- **验收**：单元回合中产物文件数随时间近似线性增长（write 事件穿插在 read 之间，事件流可直接验）；
  人为中断后已写文档不重写。

### DR-12 ·（高，用户拍板 10-23 21:06）doc-review 权限与职责重划：审查官不读码

- **用户原话**：「文档审查他看代码干鸡毛啊，这个权限没做好」。
- **现状**：doc-review profile 挂着 codegraph MCP → 审查官直接读码做事实核查（unit 2 审查：61 次工具调用、
  14.5 分钟，成本≈写作本身），把 D012 引擎侧确定性审计（coverage+lint 已算好注入）人肉重推导了一遍。
- **正确职责划分**：
  - **引擎（确定性）**：coverage（inventory 实体全覆盖）+ doc-lint（实体存在/链接/必填节）+ spec 条目
    （来自测试的行为真值锚，t003）→ 算好注入审查；
  - **审查官（文字判断）**：输入 = 单元文档全量 + 引擎注入的审计文本；职责 = 表达/结构/一致性/可读性；
    **不读码**——profile 去掉 codegraph（真源由确定性面兑底，语义残余风险由 doc-fix + 真实使用捕获）。
- **真源兑底的诚实说明**：纯不读码漏不掉「文档说错行为语义」类错误；缓解 = 把 spec 行为条目作为
  不读码的事实锚注入审查（测试即真值），残余风险由 doc-fix 阶段与使用者反馈捕获。
- **修法**：manifest doc-review.mcp 去掉 codegraph；审查提示词同步改（职责重述 + 审计文本为主输入）；
- **验收**：审查回合事件流零 codegraph/读码调用；审查耗时显著下降（与 DR-10 审查瘦身协同）。

### DR-14 ·（高，用户拍板 10-23 21:22）审查与写作流水线并行：lead=1 的无损投机

- **用户拍板**：背压 lead=1；单独立案。
- **理论依据**：单元间生成决策弱耦合（kickoff 由 gate 0 预分配，N+1 写什么不依赖 N 的裁决）→ 满足
  投机前提。对号 Speculative Actions（arXiv 2510.04371，无损加速）+ Commit Boundary
  （可逆提前工作 + 明确提交边界 + 反馈永不丢）：写 N+1 = 押注「N 过审」的投机；提交边界 = N 的裁决；
  文档可修补无不可逆副作用；FAIL 反馈入修复队列永不丢 → 无损条件全部满足。
- **业界坐标**：主流 generator-critic 反思环全是阻塞式，那是对的——前提是下一步生成依赖上一步裁决；
  本案是对该前提不成立场景的非阻塞变体。

**组件三件**：
1. ReviewWorker（每单元一线程 + 独立 RpcClient）：现行审查逻辑原样搬入（C19-R1 新实例口径、空响应重试、
   协议违例检测，DR-13 防御一并生效），裁决发 channel；
2. 裁决通道 mpsc<ReviewVerdict{unit, round, verdict, issues}>；
3. 主循环状态机：每单元 Written → Reviewing → Passed | FailQueued(→Fixing→Passed)。

**主循环规则四条**：
- 交卷(N) 即分叉：spawn 审查线程(N) + 按背压决定 kickoff(N+1)；
- 背压 lead=1：在途待裁决 ≤1，投机风险敞口硬性封顶一个单元；
- fix 优先：doc agent 每次交卷 settle 后，fix 队列非空先修后开新（绝不 mid-turn 打断）；
- 断路器：连续 2 FAIL → 停发新 kickoff（andon），修复队列清完才恢复。

**失败语义**（全部沿用已验证机制）：审查线程超时/空响应→线程内换实例重试；zombie→idle_ms 收割
按 run_id 全杀（审查 pi 也在 ledger）；全链 Failed→夜间哨兵 resume。

**观测**：新事件 review.pass/review.fail（带 unit/round/耗时）、pipeline.lead、fix.queued；
写与审的重叠在时间线肉眼可见（DR-9 验收覆盖）。

**开关**：DEVFORGE_DOC_PIPELINE=on，默认 **off**——off 时行为与现串行逐字节等价，回退零成本，上线先 A/B。

**实现规模与落点**：doc_from_zero.rs 主循环改状态机（~150 行）+ 审查线程函数（~80 行）+ channel/状态表
（~40 行）；server/mod.rs 零改动（watchdog/收割不变）；单测：乱序裁决/断路器/fix 队列优先级/双线程时序。
约一天半。

**与其余案关系**：与 DR-11（穿插）、DR-12（审查不读码）正交可独立先行；DR-12 落地后审查变短，
与写作时间更匹配，并行收益更干净。**验收**：事件流可见写与审时间线重叠；单元周期 = max(写，审)+glue；
lint/审查通过率不回退；off 模式与现行为等价。
