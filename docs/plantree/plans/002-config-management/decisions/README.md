# Decisions — P002

稳定决策记录。只记「选了什么 + 为什么 + 后果」。

## 001 · Key 明文，安全不设防

- **决策**：API Key 明文存清单，不做加密、不接钥匙串。安全维度整体不管，未来也不管
- **为什么**（用户拍板）：明文就明文，无所谓；与 pi 本机 auth.json 同一水位
- **后果**：清单文件就是敏感文件，但不需要任何额外防护设计；Q001 结案

## 002 · 模板化：基座写死，不搞通用 CRUD

- **决策**：公共基座（提示词、必装插件、skills、MCP、Key）写死成模板；Agent 间的差异收敛到极小维度（见 003）。不设计通用配置 CRUD 系统
- **为什么**（用户拍板）：所谓基座+差异覆盖，说白了就是模板——写死就可以了
- **后果**：P002 的「内部管理」大幅瘦身：不是给每类配置做通用编辑器，而是维护模板 + 少量可变项；Q003 结案

## 003 · 维护收敛律：最终只有模型可自定义

- **决策**：系统定型后，唯一长期开放的自定义维度 = **每个 Agent 用什么模型**。其余一切最终写死：提示词定稿即定死、skills 定死、MCP 就是模板的普通一员（与插件/提示词/skills 同待遇，写死，无特殊化）。唯一例外：插件版本——插件走安装模式，版本随安装流动，不锁死
- **为什么**（用户拍板）：现在全量维护是因为还要开发调试；未来做好之后东西都定死了，能自定义的就只剩模型。（2026-10-16 二次修正：MCP 不单独系统级维护，就是 Agent 配置的普通一项，归入模板）
- **后果**：① 清单 schema 按两层设计：模板层（写死）+ 模型层（每 Agent 可变）；② MCP 归入模板层，无特殊待遇；③ 自动更新主要服务开发调试期，定型后该能力自然闲置——不是问题，是终态

## 004 · 模型固定分配（固定死，不改）

- **决策**（用户拍板 2026-10-17，原话「不要给我改」）：审查 Agent → **Grok 4.7**（mokeywork/grok-4.7）；编码 Agent → **DeepSeek flash**（mokeywork/deepseek-flash）。规划 Agent 维持 DeepSeek flash 不变（延续 2026-10-16 双规划 Agent 同模型拍板）。内置清单已按此写死（model_pool 双条目 + 各 Agent 固定引用），模型 id 为 P1-CAL-01 校准后的真实 id（显示名「DeepSeek flash」/「Grok4.7」不可用作 id）
- **为什么**：维护收敛律（003）下模型分配是唯一开放维度，用户行使该维度并宣布定型——这是终态配置，不是临时调试值
- **后果**：① 任何后续测试/修复不得改动该分配；② 渲染器对模型层的唯一职责 = 把池内定义落到 profile（models.json/auth.json/settings），不得再照录显示名（已修正）；③ 未来编码阶段新建编码 Agent 时直接引用 deepseek-flash 池条目
