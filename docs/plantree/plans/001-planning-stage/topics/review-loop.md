# Topic · Review 循环

「检查 → 打回 → 修 → 重查」循环的语义定义。这是规划阶段的质量闸门。

## 循环规则

1. Plan Agent 产出/修订 plan tree 后进入暂停保活（完成判定：强制 ask-user-question 问用户，确认后输出完成标记——decisions/008）
2. 编排器 spawn **全新** Review Agent（不带任何前轮记忆，从头读 plan tree + skills）
3. Review 检查**仅限**：上下文语义是否通顺、前后是否矛盾
4. 结果二选一：
   - **通顺** → 阶段结束，Plan Agent 与本任 Review Agent 一并停止 → 编排器进入下一阶段衔接点（本 MVP 的终点）
   - **不通顺** → Review 输出问题清单（哪里不通顺/哪里矛盾）→ **Review Agent 死** → 清单回注活着的 Plan Agent
5. Plan Agent 被唤醒，依据清单修订 plan tree，修订完成进入暂停
6. 自动推进 → 回到第 2 步

## 设计原则

- **零熔断**（decisions/003）：循环次数无上限。模型治理靠 prompt 质量，不靠轮次封顶
- **Review 无状态**：每轮全新实例保证审查视角不被上一轮「带偏」（上一轮觉得有问题的地方，修完后由新视角重新全局判断）
- **干活者无损失**：Plan Agent 的上下文跨轮次连续——它记得自己写过什么、被批过什么，修订是「继续写」不是「重写」
- **结果通道可追溯**：每轮问题清单落盘（形态见 Q002），通过后就是现成的 review 历史

## 边界（刻意不做）

- 不评设计好坏、不找潜在坑、不判断「沟通是否充分」
- 不做严重度分级阻塞（那是熔断思路的变体，违背零限制哲学）
- 不允许 Review 直接改 plan tree——检查者不动手，修改权只在干活者手里（保持单一写入方，避免并发写冲突）
- **Review 永不碰用户**（用户拍板 2026-10-16）：它唯一的作用就是检查——有问题打回告诉 Plan Agent，没问题就过。拿不准（看不出是矛盾还是有意为之）= 保守按问题打回，附说明，由 Plan Agent 消化：说不清楚 → Plan Agent 去问用户（它有 ask-user-question）；之前聊过忘写 → 自己补。用户交互入口收敛到干活 Agent 自己的环节内，检查 Agent 永不交互
