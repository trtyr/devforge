# Decisions — P005

稳定决策记录。只记「选了什么 + 为什么 + 后果」，过程讨论留在 topics。

## 001 · 共享黑板 = 任务目录；代码归项目登记地址

- **决策**：共享记忆区物理上就是 `~/.devforge/plans/<项目>/<任务>/`（planning 产物已在此）；coding 过程资产入其 `coding/` 子树。目标项目代码不进黑板——写在项目登记的 `local_path`（创建项目时用户指定；从 0 创建 = 在该位置创建项目）
- **为什么**（用户拍板）：黑板之所以叫共享，是当前任务后续所有 Agent 都可见；代码跟项目走——「这个项目登进系统，它的地址就是它所在的地方」，不是写死的 workspace
- **后果**：run 归档/重跑留档策略不卷代码；黑板=交接面，跨 SOP 无需搬运；coding agent 拿双路径（黑板 cwd + 代码区注入）

## 002 · 阶段划分权在 Coding Agent

- **决策**：plan tree 不含排期/阶段；体量判断与 N 阶段划分由 Coding Agent 拿到树后自行决定，想一阶段做完就一阶段，想 ABCD 就 ABCD
- **为什么**（用户拍板）：解耦——树是领导拍板的报告，下面的人自己判断怎么分工；领导不给执行者排阶段
- **后果**：划分结果落 `coding/stages.md` 供 review 审计；编排层不感知阶段数，只认结构化标记流转

## 003 · 编码阶段只写单测，严禁端到端测试

- **决策**：Coding Agent 只写保证自身代码正确的单测；e2e 一律不写，归测试阶段
- **为什么**（用户拍板）：e2e 真的很浪费时间
- **后果**：review 不要求 e2e；e2e 诉求由测试阶段 SOP 承接

## 004 · 文档与代码伴写；文档以「可据此写测试」为验收

- **决策**：写代码同时写文档，禁止分阶段补写；文档详细程度以「第三方（未来的测试 Agent）能完全基于文档写测试」为准
- **为什么**（用户拍板）：分开看似解耦，实则单纯浪费上下文；测试 Agent 要吃文档
- **后果**：Review 增设文档审查面（漏写=打回）；测试阶段立项时接口面已天然就绪（文档规范即接口，P005 不再深入设计）

## 005 · plan 偏差协议：多重自查在前，问用户兜底，全程留痕

- **决策**：发现 plan 有问题先停下；问用户前必须过自查门槛（重读树/文档排误读 → CodeGraph/web/context7 搜索排技术过时）；仍存疑才 ask-user-question。用户裁决三种：给新决策=更新树+留痕；授权代选=自定+留痕；跳过=不动树只留痕。留痕一律落 `coding/blockers/`（发现依据/问题位置/裁决）
- **为什么**（用户拍板）：跟用户沟通的内容 plan 阶段就该解决完；到了 coding 再问用户必须经过非常多的评审
- **后果**：树编辑权只在此协议内行使；流水线可经 blockers/ 感知阻塞

## 006 · 语言 skills 严禁自写：搜索→下载→原样 vendor

- **决策**：四语言（Rust/Go/Python/TS-JS）的最佳实践 skills 一律外部搜索现成品，下载后原样移入分发，不重写
- **为什么**（用户拍板）：自写必带个人偏好与知识截点的过时压缩（库里 A 方案好，现状已是 B，手写就 A/B 共存）；以外部搜索结果为准
- **后果**：skills 内容 = 最佳实践+约束约定（非技术文档）；采购发生在实现期（T003），来源与版本入 evidence

## 007 · CodeGraph/context7 MCP：per-agent stdio，配置统一入渲染

- **决策**：两 MCP 均以 stdio 形态写进 profile 的 mcp.json（pi 原生机制），随各自 pi 进程生灭；系统对 pi 的台账管辖（P001 decisions/007）传递覆盖。并发任务 = 多实例共享同一 `.codegraph/` 索引（FileLock 仲裁 + auto-sync 保新鲜）
- **为什么**（用户原想系统级单例，侦察后修正）：`codegraph serve --mcp` 仅 stdio 传输（父子进程），真单例需自研复用桥，MVP 变重；per-agent 实例无孤儿风险、零新增编排代码，系统级管辖经 pi 台账已达成
- **后果**：单例桥入 Deferred（实测争用才评估）；CodeGraph 索引由 Coding Agent 开工自检 `codegraph init`（索引是你的决定——工具设计哲学）；默认单工具 `codegraph_explore` 够用，不开放全工具面

## 008 · 刚需架构条款写死提示词

- **决策**：Coding Agent 提示词强制四条——AI-friendly 架构；健全的错误处理与回退系统；审计/日志/行为审查系统；错误责任分布制（每个错误可定位到模块）。Review 对应设审查面
- **为什么**（用户拍板）：刚需，不是建议
- **后果**：AI-friendly 定义以外部检索为准（实现期核实，不入自由发挥）

## 009 · git 策略：阶段 PASS 即 commit（2026-10-18 拍板）

- **决策**：每阶段 review PASS 后，Coding Agent 在项目当前分支 commit——锚点即续作参照与回滚点；commit 由 coding agent 执行，不 push
- **为什么**（用户拍板）：AI 要在用户仓库动刀，必须有清晰的落点与回滚锚；从零项目天然合理，已有项目直接进当前分支（不另开分支）
- **后果**：断点续作有硬参照（commit 历史+工作区现状）；测试阶段接手时代码状态明确；用户随时可 git 审查/回滚 agent 的工作

## 010 · 断点续作：新实例自判续作/重做（2026-10-18 拍板）

- **决策**：run 中断后重跑，新 coding 实例的初始提示词含勘察义务——代码区已有实现时，先勘察现状（含 git log），自行判断续作（接着未完阶段干）还是重做
- **为什么**（用户拍板）：与阶段自治同一哲学，判断权在 agent；黑板 coding/ 随 run 归档不假，但代码区现状+commit 锚点足以支撑判断
- **后果**：提示词必须含「先勘察后动工」义务；编排层不做进度迁移，新 run 从全新黑板起步

## 011 · 树完成判定锚点 = 对照实物（2026-10-18 拍板）

- **决策**：Review 判定 finish/advance 拿树的目标逐项对照**实际代码与文档**核验；stages.md 只是过程管理工具，不作为验收依据——agent 划漏了任务也蒙混不过
- **为什么**（用户拍板）：「不能自己没完成就绕过那个东西自己给它打勾」的延伸——连阶段划分本身也要受实物检验
- **后果**：Review 必须真读代码真跑单测（实地验证，不信任自报）；finish 判定成本随树体量上升（接受，零限制哲学）

## 012 · 阻塞通道 = dialog 挂起（2026-10-18 拍板）

- **决策**：「流水线检测到阻塞」由 ask-user-question 的 dialog 挂起承担——run 挂起等答案即系统可见的阻塞态（现有 ui relay 通道）；blockers/ 纯留痕，不做文件监视器
- **为什么**（用户拍板）：现有通道够用，不增机制
- **后果**：未走 ask 静默写 blockers/ 的情形系统不主动感知（提示词纪律约束）；cancel 解除 dialog 挂起的能力（P001 已修）直接复用

## 013 · CodeGraph 战略地位：代码事实层，codegraph-first 纪律（2026-10-18 拍板）

- **决策**：CodeGraph 定位为流水线的**代码事实层**（plan tree=语义意图，CodeGraph=代码结构真相，两者之桥），非普通供给。落地四件：①codegraph-first 纪律写进双 agent 提示词（结构问题先问图，禁 grep-read 爬取；改前必看 impact；交 review 前 affected 自查测试缺口）；②索引 init 归引擎 spawn 前预检（agent 兑底）；③路径错位用 projectPath 传参教给 agent（Q004）；④MCP 维持单工具 explore，impact/affected/callers 走 CLI。分场景用法矩阵见 topics/codegraph-strategy.md
- **为什么**（用户拍板）：战略性工具——省轮次（对冲中转长 turn 风险 P8-ISSUE-06）、审得动（decisions/011 对照实物逐项核验的可行性前提）、接得住（产出贴现有架构长）；索引是项目持久资产，跨 run 跨 SOP 越用越新鲜
- **后果**：引擎新增预检步骤（T006）；两份提示词都带纪律条款与场景矩阵（T004/T005）；遥测关闭（CODEGRAPH_TELEMETRY=0）
