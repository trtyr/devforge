# Topic · Coding Agent

Plan Agent 的同门师兄弟：底座同为 pi RPC 长驻进程，上下文全程保持——除非整个 coding SOP 结束，进程不死；review 打回、阶段推进都在同一进程内以新 prompt 驱动（decisions/004 保活模式沿袭）。

## 三层流程（解耦：树不排期，执行者自判）

1. **承上**：读黑板上的 plan tree，自行判断体量（庞大/小巧），自行决定分 N 个阶段——树是「领导的报告」，怎么分工是下面人的事；划分落 `coding/stages.md`
2. **制 todo**：对当前阶段分析实现路径，产出 todo list 落 `coding/todo.md`（rpiv-todo 插件管理方向感）
3. **干活**：按 todo 逐项开发，阶段自认完成后输出结构化完成标记，交 Review

## 开发纪律

- **文档伴写**：写代码的同时写文档（`coding/docs/`），严禁「先码后补」——分开看似解耦实则浪费上下文（decisions/004）；文档验收标准 = 第三方可据此写测试
- **测试纪律**：只写单测保证自身代码正确；**严禁端到端测试**——费时且归测试阶段（decisions/003）
- **刚需架构条款**（写死在提示词）：AI-friendly 架构；健全的错误处理与回退；审计/日志/行为审查；错误责任分布制——每个错误能定位到所属模块（decisions/008）

## plan 偏差协议（发现 plan 有问题：停下，不擅自绕）

提问前置门槛（过了才许问用户）：重读树与文档确认非误读 → 用 CodeGraph/web tools/context7 搜索求证非技术认知过时 → 仍存疑才 ask-user-question。

问后必留痕（`coding/blockers/`）：基于什么发现、plan 问题在哪、用户最终裁决。三种裁决的处理：

1. 用户给新决策 → 更新 plan tree + 留痕
2. 用户授权代选 → 按己见更新树 + 留痕（决策权转移也记录）
3. 用户说跳过 → 不动树，只留痕

初衷：能在 plan 阶段解决的不带进 coding；进来了也尽量自己消化，问用户是最后手段。
