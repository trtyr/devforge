# 决策记录（`010-run-resume`）

> 追加式：新决策往下加，不改旧条目；与旧条目冲突时写「取代 Dxxx」。

## D001 · 断点真源只有黑板一份，且**按 SOP 分文件**（2026-10-20）

- **决策**：运行状态写 `plans/<project>/<task>/<sop>/state.json`——按 **project + task + SOP** 三级隔离，**不是一个 task 一份**。产物目录**不再存放运行状态**。
  - 同一个 task 同时跑 `doc-from-zero` 和 `change`，两份状态互不覆盖；同一个项目不同 task 各管各的。
  - 同一 SOP 重复跑（含 `fresh`）就落在同一个文件上——续跑的对象就是它。
- **状态自证身份**：文件内必存 `schema_version` / `sop` / `project` / `task`（引擎写、加载时校验）。路径虽已隔离，但如果有人把文件拷错位置或手改，**四者与当前请求不一致就拒绝续跑、按冷启动处理并记 WARN**——宁可重跑，不猜。
- **不设镜像**：`docs/contexts/_meta/state.json` 这类「产物目录里再抄一份」的方案被否——两份状态必然漂移，冲突时还得再定谁作数。
- **作废即作废**：历史轮次写在产物目录里的 state 不迁移、不兼容读取。
- **与并发的关系**：并发粒度仍按现有串行 guard（同一 task 同时只能一个 run）；本决策解决的是「同一 task 在不同时间/不同 SOP 之间串味」，不是放开并发。
- **理由**：产物是给人看的、可被清理重生成的东西；运行状态是机器进度，删产物不该等于丢断点；而「一份状态装所有 SOP」会在多流程并行时互相覆盖。

**拍板**：用户 2026-10-20（指出「同一个项目我同时跑文档、跑 MVP、加功能，不能都落在同一个 state.json」）。

## D002 · `start` 默认续跑，`fresh` 才重来（2026-10-20）

- **决策**：`POST /projects/<p>/tasks/<t>/start` 默认**续跑**——黑板有未完成 state 就接 `done` 之后推。显式 `{"fresh": true}` 才忽略并清空检查点、重做全部单元（产物目录不删，由 agent 重写）。响应回显 `resumed: true|false`，调用方不必猜。
- **为什么默认续跑**：掉线重连、进程重启后重发同一条请求是常态；要求人记得加 `resume=true` 就是让人为机器状态负责。
- **为什么不强制续跑**：调试与验收需要从零验证（`fresh` 就是那个出口），强制续跑会把这条出口堵死。

**拍板**：用户 2026-10-20。

## D003 · done 必须自校验：名单不算数，证据才算（2026-10-20）

- **决策**：单元 PASS 时由引擎与 SOP 共同记录该单元的**完成证据**（doc：产出文件清单 + lint 退出码）。续跑开头逐条复核，证据不成立（文件缺失、门禁变红）就把该单元从 `done` 摘掉重做。
- **理由**：历史教训——一轮 28 PASS 全绿的 run，产物实际少一个单元，只靠 state 与 inventory 对账才发现。「run 说我做完了」与「事真做完了」必须是两回事。
- **边界**：复核只做**机械可判定**的事（文件在不在、命令退出码）。语义判断（文档写得好不好）归审查，不归复核。

**拍板**：用户 2026-10-20。

## D004 · 基础设施故障自动重启最多 3 次，质量失败不重启（2026-10-20）

- **决策**：`DevforgeError::System` 类失败（上游 5xx、审查空回复、子进程瞬时死）→ 引擎自动重启同一 run，**最多 3 次**，退避 10s/30s/90s，每次从断点继续（不重做已完成单元）；3 次仍失败判 `Failed` 等人。
- **不自动重启的**：审查 FAIL 打回、协议违例达上限、越界申报、验收不通过——这些是**质量判断结果**，重启只会重复同一个结论，还会掩盖计划/实现问题。
- **实现口径**：代码层用 `DevforgeError::Quality` 表达质量失败（与 `System` 分开），`map_intervention` 把它映射为 `RunOutcome::Failed`，不进重试分支。无标记重推达上限（agent 连续不配合）也归质量失败——重启一个不合作的 agent 无意义。
- **与「零硬限制」的关系**：无标记重推、审查轮次的天花板已在 005/015、007/D013、009/D020 定过；这里再补一条运行级上限，同一原则——**进度循环设界，质量循环不设**。

**拍板**：用户 2026-10-20。

## D005 · 引擎与 SOP 的分工（2026-10-20）

- **引擎**：状态文件位置与原子写、`start` 续跑/fresh 语义、done 复核的调度、故障重启、公共状态壳（`sop`/`updated_at`/`attempt`）。
- **SOP**：状态里的扩展段结构、`done` 的证据定义与复核实现、恢复时给 agent 的开工语、要重做哪些单元。
- **为什么这样切**：续跑对每个 SOP 都一样（存哪、怎么触发、挂了怎么办），能做成一份；而「什么算一个单元做完」每个 SOP 完全不同，硬塞进引擎就变成开关堆。
- **接口形状**：SOP 实现一个 `Resumable` 风格的小 trait（状态路径、证据复核、恢复语），引擎在 `start` 与重启路径里统一调用——不引入第二套状态机。
- **派发契约（审计后补写）**：SOP 循环拿到的单元列表就是「本次要跑的全部」（引擎已按续跑计划算好 to_run），**循环不得再用 `is_done` 二次过滤**；重做单元派发前先把旧 `done` 记录摘掉（崩溃时不留下假绿）。

**拍板**：用户 2026-10-20。

## D006 · 引擎可观测性三件套 + 渲染闸门（2026-10-22）

- **决策**：引擎对自己内部发生了什么**事后查得出来**——三件交付物，外加一处根因修复：
  1. **原始错误全量可见**：每次尝试失败在**决定重试之前**落一条分级条目（`event="run.attempt_failed"`，
     字段：`component` / `attempt` / `error`（顶层 Display 逐字）/ `error_chain`（source 链逐层，`→` 连接）/
     `retryable`）；四次尝试耗尽再落一条 `event="run.attempt_exhausted"`（含总尝试次数）。
     **分级口径**：质量类失败（`DevforgeError::Quality`）落 **WARN**，其余一切失败落 **ERROR**——质量失败不重启，
     不该占 ERROR 级别。两个落点（重试层 / `map_intervention` 的质量分支）**字段集完全同构**，
     `attempt` 由 run 上下文统一给出（同一线程 → 同一份真相）。
  2. **里程碑**：阶段转换、每轮 fix 起止、每次审查开庭（含轮次）、每道机械门的判定，各落一条结构化 INFO。
     事件名固定八个：`phase.change` / `fix.start` / `fix.end` / `review.open` / `gate.baseline` /
     `gate.self_check` / `gate.step_commits` / `agent.turn_end`；重试侧另两个（`run.attempt_failed` /
     `run.attempt_exhausted`）。`target` 由发出它的模块自动给出 → 里程碑必须**内联**写在调用点（包装函数会让
     全部里程碑共用一个 target，「按 target 过滤」这条需求直接作废）。覆盖面：change 编排层 + MVP 三循环 +
     doc 两处；agent 轮次结束的落点**唯一**（`src/engine/client.rs`——一处覆盖全部 SOP，同一轮不出现第二条）。
  3. **死亡取证**：① panic hook 写墓碑（panic 原文 + 位置 + 当时阶段/步骤）——写入 **best-effort**，
     **绝不**在 hook 里二次 panic（那会 abort，连 stderr 链回都丢），无论成败都**链回上一个 hook**；
     ② run 心跳（阶段 / 步骤 / 时间戳 / attempt，**覆盖写**）——事件驱动 + watchdog 低频兜底刷新：
     run 停在同一阶段、长时间无事件时时间戳仍向前走 → 能区分「卡死」与「已死」。
     落点 = 观测根（`HOME/.devforge` 下的 `heartbeat/` 与 `tombstones/`），**按 run 捕获** → 一次 run 的证据落点固定，
     不随进程级注入漂移。
- **渲染闸门（根因修复）**：`PUT /api/v1/config/manifest` 的渲染在后台进行，而 `POST .../start` 不等渲染就开跑
  → 门卫在半渲染的 profile 上判「未渲染」→ 抛裸 `System` → 被判成基础设施故障 → **盲重启**（boot 六连的根因）。
  口径：**开跑前等所需 profile 的 `settings.json` 落盘**（门卫的判据，早于装包 → 秒级；**不等**整轮渲染；
  渲染结束/失败也会结束等待）；等待用可 await 的原语，不占 tokio worker。
- **「profile 未就绪」改判配置错误**：该失败的错误种类从 `System` 改成 `Config` → 不被判为基础设施故障
  → **不自动重启**，第一次就以明确错误失败（错误文本一字不改）。
- **理由**：三次实测事故指向同一病根——引擎在自己内部发生了什么，事后查不出来（原始错误从不落盘；
  交卷到重审开庭之间是 15 分钟的空洞；进程猝死时连「死在哪个阶段」都答不出）。
  可见性同时是**根因修复的前提**：没有 ERROR 落盘，boot 期到底败在哪只能猜。
- **边界**：不改重试策略本身（4 次尝试、10s/30s/90s 退避）；不改任何 SOP 的业务判定（审查三通道、
  质量失败不重启、越界门、验收对账口径一律不动）；三道机械门**门本身不改**，里程碑只落在调用点；
  panic hook 是进程级全局 → 验收测试放独立测试二进制。
- **遗留**：① 里程碑日志**不保证零丢失**（进程猝死时缓冲区最后几条可能丢）——它是过程记录，墓碑与心跳才是硬证据；
  ② 观测根默认仍是 `HOME/.devforge`（换用户 / 容器场景未定）；③ 闸门**没有兜底上界**（渲染线程挂死则 start 一直等）——
  本靶刻意不引入新超时；④ run 上下文是进程级单例，将来并发化后心跳/墓碑会互相覆盖（当前串行，暂不冲突）；
  ⑤ 心跳是覆盖写 → 「本 run 发生过几次阶段转换」要查里程碑日志，不能只看心跳；⑥ 闸门让「先 PUT 清单再 start」
  的 e2e 脚本的 start 变成可能等待的端点（脚本改动不在本靶白名单）。

**拍板**：用户 2026-10-22（Q1 = 渲染闸门；Q2 = 原始错误落盘分级：基础 ERROR / 质量 WARN；Q3 = 里程碑全 SOP 全覆盖）。
