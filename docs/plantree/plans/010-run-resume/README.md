# 运行续跑与韧性（run 生命周期）· 框架

> 2026-10-20 立项。背景：自文档化连挂两轮（运行目录被清、审查上游 500），两轮都只能从零重来。
> 目标：**任何 SOP 的 run 都能断点续跑，并从基础设施故障里自己站起来**。

## 一句话边界

- **做什么**：run 的状态持久化位置、`start` 的续跑语义、done 的证据复核、基础设施故障的自动重启。
- **不做什么**：任何 SOP 的业务语义。什么算「一个单元做完了」、恢复时该对 agent 说什么、要重做哪些单元——**归各 SOP 自己声明**。

这条边界是本次立项的直接原因：第一版把「续跑」写进了 `008-doc-from-zero`，被指出「这个跟文档有什么关系？别的 SOP 完全也能用」——它确实是引擎级能力，SOP 只是接入方。

## 现状（2026-10-20 实测）

| 问题 | 现象 |
| --- | --- |
| 断点位置错 | `doc-from-zero` 的 `state.json` 住在目标仓 `docs/contexts/_meta/`——**运行状态寄居在产物目录**，清产物即丢断点；且与「产物目录只放给人看的文档」职责冲突 |
| 失败即死 | 上游 500 / 审查空回复 / 进程瞬时死 → run 直接 `Failed`，没有自动重启，全靠人再发一次 `start` |
| 假绿 | `done` 只是一份名单；产物被删、lint 变红，续跑照样跳过该单元（历史教训：28 PASS 全绿，产物其实少一个单元） |
| 没测过 | e2e 硬要求「目标仓初始无 docs/contexts」，系统性地只测冷启动 |

## 引擎提供 vs SOP 提供

| 能力 | 归属 |
| --- | --- |
| 状态文件位置、原子写、损坏容错、按 SOP 隔离 | **引擎** |
| `POST .../start` 默认续跑、`{"fresh": true}` 重来、响应回显 `resumed` | **引擎**（API 语义，所有 SOP 一致） |
| 基础设施故障自动重启（次数/退避/终态） | **引擎** |
| 状态的公共壳（sop 名、phase、updated_at、重试计数） | **引擎** |
| 状态里的扩展段（哪些单元、哪些步、验收项） | **SOP** |
| `done` 的证据与复核（产物在不在？门禁还绿不绿？） | **SOP** 实现，引擎在恢复时调用 |
| 恢复时给 agent 的开工语 | **SOP** |

一句话：**引擎管「怎么续」，SOP 管「续到哪、凭什么算做完」**。

## 接入方一览

| SOP | 状态的单元 | done 的证据（复核什么） |
| --- | --- | --- |
| `doc-from-zero` | unit-xxx | 产出文件清单存在 + `doc-lint` 退出码 0 |
| `planning` | 阶段（暂不续跑：无长单元） | — |
| `coding` | impl step | commit sha 存在 + 该步目标测试绿 |
| `testing` | acceptance item | 对账到的 `path:line` 仍存在 |
| `change` | phase（coding/testing/done）+ roundtrips | 与 P009 D022 统一（见 Q001） |

## 口径（详见 `decisions/`）

- 断点真源**只有黑板一份**，且按 **project / task / SOP 三级分文件**（`plans/<project>/<task>/<sop>/state.json`）——同一 task 下 doc 与 change 两份状态互不覆盖，状态内再存 `sop`/`project`/`task` 自证身份，与后者不一致即拒绝续跑。
- `start` **默认续跑**，`{"fresh": true}` 才清检查点重做。
- 续跑前**先复核 done**：证据不成立就踢回未完成，重做该单元。
- 基础设施故障（`DevforgeError::System` 类）**自动重启最多 3 次**（10s/30s/90s 退避），3 次仍败才 `Failed`。审查打回、协议违例、越界申报**不**算故障，不自动重启。
