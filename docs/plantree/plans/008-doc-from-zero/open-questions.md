# doc-from-zero · 未决问题（框架期）

## Q001 · 产物落在哪里？

- 选项 A：落在**被documented的仓库**里（`docs/` 或 `docs/contexts/`）——文档跟代码同仓，第三人可直接看
- 选项 B：落在**黑板**（devforge 系统侧 `~/.devforge/plans/...`）——与 SOP-1 一致，不改动别人的仓库
- 选项 C：双写（黑板为工作区，通过审查后导出到仓库）

考虑：陌生项目可能不让写（只读挂载）；但文档的最终价值是跟着代码走。

## Q002 · inventory 的抽取器用什么？

- codegraph（已有，走 MCP/CLI）能覆盖模块树与入口点，但**语言支持有限**
- 需要补：路由表、CLI 命令、配置键、schema —— 这些是"约定"层面的，可能需要语言特定的轻量脚本
- 是否可以接受「多语言 = 多抽取器适配」的成本？还是先只支持 Python/TS？

## Q003 · 与现有 doc-init skill 的关系

**已关闭（2026-10-19 D001）**：doc-init 退役，本 SOP 为唯一权威；其工程教训以 D002 吸收为红线。

## Q011 · 还要不要画图

旧 skill 2026-10-12 拍过“纯文字、不画图”（存根图/宣告图失败率高）。P008 原框架写了架构图。
- 选项 A：不画图（沿用旧拍板）——阶段 3 只产文字与 Mermaid 源码
- 选项 B：画但只产 Mermaid 源码，不渲染成图（渲染交给前端/主 Agent）
- 选项 C：画图（架构图/数据流图），接受渲染失败成本

## Q012 · 置信度标记放哪里

- 选项 A：行内标（🟢 紧跟在断言后）——可读性差但机器可扫
- 选项 B：旁挂文件（`confidence-report.md` 逐条对应）——终稿干净，但要维护对应关系
- 选项 C：旁挂但只标 🟡/🔴（终稿里默认即🟢，不标）——最轻，但“默认视为事实”会让标错更难发现

## Q013 · 旧 `docs-update` 链怎么办

旧 skill 的增量对齐能力（`docs-update`）不在本 plan 范围，但 doc-init 退役后它失去上游。
- 选项：本 SOP 内置增量模式（清单差异→只重写变动模块）；或单独立项

## Q004 · 并行度与一致性

并行写作时，同一概念可能被不同 agent 用不同术语描述。
是否需要一份**术语表**（glossary）在写作前统一？（CodeWiki 的做法是全局引用登记表 + 汇编时归一）

## Q005 · 审查者的角色

- 复用 doc-review（极简、只审文档一致性）？
- 还是需要一个"文档审查官"变体（要跑 codegraph 查实体存在性、要能手算覆盖率）？

## Q006 · 完成判据的严格程度

- 严格：inventory 覆盖率 100% 且真实性 100% 才 PASS
- 现实：允许显式缺口（"这部分代码无行为可文档化" / "反编译产物"），但缺口必须登记成 finding

## Q007 · doc-lint 的形态与归属

- 被 document 的仓库里当脚本；还是 devforge 侧工具作用于任意工作区？（后者通用，但要处理多语言）
- 与 `topics/doc-contract.md` §六 规格对齐

## Q008 · 必填节的严格度

- 缺一项就 FAIL，还是按条目重要性分级（入口点严格、内部函数宽松）？

## Q009 · `doc_level` 默认档

- 三档（essential / complete / detailed），默认建议 **complete**
- 是否需要像 Reversa 那样在勘察后询问调用方？（我们是全自动 SOP，可能固定默认 + API 参数覆盖）

## Q010 · 置信度标记的落地形式

- 写法：行内 `🟢` 标记 vs YAML front-matter vs 独立断言清单？
- 审计怎么机判“标了 🟢 但其实给不出 path:line”——正则扫描可行，但“重放命令”需要工具支持
- 无 git 场景下，ADR/业务规则类内容是否一律强制 🟡？
