## Q001 · 产物落在哪里？

- 选项 A：落在**被documented的仓库**里（`docs/` 或 `docs/contexts/`）——文档跟代码同仓，第三人可直接看
- 选项 B：落在**黑板**（devforge 系统侧 `~/.devforge/plans/...`）——与 SOP-1 一致，不改动别人的仓库
- 选项 C：双写（黑板为工作区，通过审查后导出到仓库）

考虑：陌生项目可能不让写（只读挂载）；但文档的最终价值是跟着代码走。

## Q002 · inventory 的抽取器用什么？

- codegraph（已有，走 MCP/CLI）能覆盖模块树与入口点，但**语言支持有限**
- 需要补：路由表、CLI 命令、配置键、schema —— 这些是"约定"层面的，可能需要语言特定的轻量脚本
- 是否可以接受「多语言 = 多抽取器适配」的成本？还是先只支持 Python/TS？

## Q003 · 与现有 doc-init skill 的关系

- 直接复用（SOP 就是 skill 的编排版）
- 还是重写（skill 只保留"从零认识仓库"的轻量用途）

## Q004 · 并行度与一致性

并行写作时，同一概念可能被不同 agent 用不同术语描述。
是否需要一份**术语表**（glossary）在写作前统一？（CodeWiki 的做法是全局引用登记表 + 汇编时归一）

## Q005 · 审查者的角色

- 复用 doc-review（极简、只审文档一致性）？
- 还是需要一个"文档审查官"变体（要跑 codegraph 查实体存在性、要能手算覆盖率）？

## Q006 · 完成判据的严格程度

- 严格：inventory 覆盖率 100% 且真实性 100% 才 PASS
- 现实：允许显式缺口（"这部分代码无行为可文档化" / "反编译产物"），但缺口必须登记成 finding
