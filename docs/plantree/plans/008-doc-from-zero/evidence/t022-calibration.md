# T022 · 速度与成本校准（基于 4 轮实测）

**数据来源**：`evidence/t021-m3-e2e.md` 的四轮单仓实证（无文档、无 git 的小 Python 仓，2 个单元）。
**结论先说**：速度问题不在门 0（秒级），而在**每次单元会话的上下文重发**——一个 40 行的仓烧了 1000 万 input token。

## 实测

| 轮次 | 结果 | 墙钟 | 单元 | 审查轮次 | token |
| --- | --- | --- | --- | --- | --- |
| 1（挂死） | 审查官死亡 → run 挂 50+ min | — | 1/2 | — | — |
| 2 | 假绿（漏第二单元） | 900s | 1/2 | 1 | 未记账 |
| 3 | 真绿 | 1230s | 2/2 | — | 未记账 |
| 4 | 真绿 + 完整账单 | 1380s | 2/2 | 2 | **10.07M**（in 9.94M / out 131k） |

拆开看（第 4 轮）：
- 门 0（清单 + 闭包 + 词表）：亚秒级，不是瓶颈；
- 每单元约 7–10 分钟，其中 doc-agent 一次会话 ~500KB 会话文件；
- 审查 2 轮、问题 0——**摩擦成本主要在「写」不在「审」**；
- input : output ≈ 76 : 1。输出只有 131k，说明绝大部分 token 是**每回合重发的上下文**。

## 这意味着什么

1. **单单元上下文必须瘦身**。现在 agent 每轮都把 facts/interpretation/已有文档串起来重发；40 行仓尚可，8 个模块的仓很容易上千万 token/单元。
2. **门 0 不需要调参**——它足够快，把它做细（T002/T003 已加）不会拖慢流程。
3. **不要加产品侧硬超时**（D002 口径不变）。第 1 轮的挂死不是慢，是「子进程死亡后阻塞读」——已按「子进程状态判死」修复，不是靠超时解决的。

## 下一步可做的（按性价比排）

1. **facts/interpretation 只注入摘要而非全文**：给下一单元的 kickoff 只带词表 + 上一单元的文件清单，不带正文。
2. **文档目录按类型分片**（第 4 轮 agent 自己的组织已证明可行），审查时只给本单元目录树而非全库。
3. **单元批量**：同一顶层目录下的相邻模块合并为一个单元（现在按顶层目录分组，已经是这个粒度；再合并会伤审查可读性，暂不建议）。
4. 观察真实仓（itsdangerous，8 模块）的用量，再决定要不要给 `doc_level=essential` 之类的低档选项做成本控制。
