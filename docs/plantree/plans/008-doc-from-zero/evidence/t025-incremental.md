## 四、召回与「不重写」证据（机械校验）

- **未受影响单元不被重写**：beta 的 5 个产物文件 `mtime_ns + size` 两轮**逐字节相同**（如 `beta/beta_count.md` mtime `1792481950290253226` / 4372B 前后一致）。
- **受影响单元被重写**：alpha 的 5 个产物全部更新，且**新增** `alpha/alpha_extra.md`（清单重建后新函数有自己的条目文档）。
- **召回**：新函数名 `alpha_extra` 出现在 5 篇文档（`runbook-alpha.md`、`alpha/a.py.md`、`alpha/alpha_sum.md`、`alpha/alpha_extra.md`、`alpha/index.md`）——变更点没有被漏写。
- **基线推进**：第 1 轮后 `base_sha = fa727add…`（= 当时 HEAD），第 2 轮后 `= adb05196…`（= 新 HEAD）；中间那次失败会保留旧基线（单测 `base_advances_only_on_pass` 锁死）。

## 五、结论与诚实边界

**结论**：doc-from-zero 从「只能从零」升级为「可增量」。小 fixture 上增量轮墙钟与 token 各省约一半；影响集合与人工判断一致，零漏召、零误重写；降级路径按设计工作。

**诚实边界**：
1. 两单元小仓，单元数放大后的收益（跳过 N-1 个单元）未实测——但机制是「只派受影响单元」，收益随单元数线性放大，方向明确；
2. 「删除/改名符号 → 引用方单元进集合」这条传播路径由单测 `deleted_symbol_pulls_in_referrers` 覆盖，本次 e2e 只走了「新增函数」路径；
3. 账单累计口径是 `docgen::usage` 的既有行为（扫目录全量），不是增量引入的；若要「按 run 精确记账」需在 usage 侧按会话文件时间过滤，另立任务。
