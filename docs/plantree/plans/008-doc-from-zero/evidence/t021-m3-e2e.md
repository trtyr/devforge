## 为什么用 fixture 而不是直接啃陌生大仓

M3 的验收问题是「SOP 能不能把一套文档从零产出来、并过五项审计」，不是「模型够不够聪明」。
所以第一个见证用**受控 fixture**：无文档、无 git、规模小到能看懂全貌——这样任何失败都先归因到流程，而不是归因到仓库复杂度。

fixture（`tests/e2e/test_22_doc_from_zero.py` 内联生成）：

```
book-app/
├── main.py            # 入口，import booklib.core
└── booklib/
    ├── __init__.py
    └── core.py        # add_book / list_books（公开）+ _reset_for_tests（私有）
```

四类诱因是刻意埋的：
- `main.py` 是入口 → 入口可达闭包有真实路径可走；
- `booklib/` 是子包 → 单元划分与导入解析要能解析 `booklib.core`；
- `_reset_for_tests` 私有 → 符号覆盖只收公开符号，不能把私有当必填；
- **完全没有 docs、没有 .git** → 文档必须凭空长出来，不许借 git 历史。

## 验收断言（脚本里可判的部分）

| 面 | 断言 |
| --- | --- |
| 门 0 | `_meta/inventory.json` 落盘；每个 module 条目都带 `unit_id`；`_meta/glossary.md` 自动导出；`_meta/gate0-closures.md` 有闭包证据 |
| 单元滚动 | `_meta/state.json` 存在且 `done` 非空；`docs/contexts/` 下出现正文 `.md` |
| 执行取证 | `sessions/doc` 与 `sessions/doc-reviews` 都有内容（写方与审方都真跑过，不是脚本自嗨） |
| 终审 | `_meta/runs/<run-id>/report.md` 存在，含「单元完成 / 审查轮次」 |
| 复算 | `devforge doc-audit <docs> --repo <repo>` 退出码 0（覆盖 + lint 的机械部分现场重算，不信 run 的自述） |

最后一条是这套 SOP 的立身之本：**证据必须能被第二个人重算**。所以脚本不读 run 的结论，自己调 CLI 重跑一遍审计。
