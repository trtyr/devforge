# 文档契约（doc-contract）· 草案

> 2026-10-19 立项讨论产物。**跨 SOP 共用**：coding 写文档、coding-review 审文档、doc-fix 补文档、P008 反向写文档——**一份契约，四处共用**，避免四份漂移。
> 状态：草案，待拍板后落地为 skill + 工具。

## 一、为什么要它

现状：文档质量靠提示词里的自然语言要求（"第三方能据此写测试"）。问题有二：

1. **不可判**——"够不够"没有机械判据，reviewer 只能凭感觉
2. **四处各写**——coding/审查/doc-fix/反向写作各有一套措辞，容易漂

结论（呼应 GitLab playbook 的 "Constraints are multipliers"）：**把规则从提示词搬到可执行的门禁上**。

## 二、三条使用方式

```
① 契约（本文件 → 未来落成 skill `doc-contract`）
② 门禁（doc-lint 工具：确定性检查，见 §四）
③ 提示词（只加一行引用：文档按 doc-contract 写；发 stage-complete 前 doc-lint 零违规）
```

## 三、条目模板（按类型）

### 3.1 入口点（CLI 命令 / HTTP 端点 / 事件处理器 / 公开导出）

必填：**用途** · **输入**（参数/请求体：名、类型、必填、默认）· **输出**（响应/返回：形状、示例）· **错误**（错误码/状态码、触发条件、错误体形状）· **示例**（可直接复制执行）

### 3.2 公开函数 / 方法

必填：**摘要**（一句话说做什么）· **行为语义**（边界条件、幂等性、副作用）· **Args**（类型、约束、默认）· **Returns** · **Raises**（异常类型与触发条件）· **示例**（可选，公开 API 建议有）

### 3.3 类

必填：**摘要** · **职责边界**（做什么 / 不做什么）· **构造参数** · **公开属性**（含义、可变性）· **典型用法**

### 3.4 配置项

必填：**名称** · **类型** · **默认值** · **是否必填** · **影响面**（改了会怎样）· **示例**

### 3.5 数据模型 / 存储

必填：**字段**（名、类型、约束、可空）· **索引/唯一约束** · **生命周期**（谁写、何时删）· **迁移注意**

### 3.6 错误码表（若系统有错误契约）

必填：**码/标识** · **含义** · **触发条件** · **客户端应如何处理**

## 四、反模式（禁止项）

| 反模式 | 为什么禁 |
|---|---|
| 复述代码（把实现抄一遍） | 代码改了文档必错，且没有增量信息 |
| 整段粘贴日志/输出 | 噪声，且无法验证 |
| `TODO` / `TBD` / "后续补充" | 未完成就是未完成，不许伪装 |
| 承诺未实现的行为 | 文档说的必须是代码做的 |
| 引用不存在的实体 | 幽灵引用（DocAgent 实测：不查真实性，朴素写法存在率仅 61%） |
| 用篇幅凑"完整" | 密度原则：篇幅由信息量决定 |

## 五、真实性规则（机械可判）

1. 文档中提到的每个**代码实体**（函数/类/方法/端点/配置键/路径）都必须真实存在
2. 引用必须可回指（`path:line` 或符号全名）
3. 汇编层（总览/架构）出现的每个新事实都必须能追溯到叶子证据——**上层断言不可凭空**

## 六、doc-lint（确定性门禁）规格

| 检查 | 实现思路 | 判定 |
|---|---|---|
| 实体存在性 | 抽取文档中的符号/路径/配置键 → 查代码（codegraph / grep / 配置文件解析） | 任一不存在 → FAIL，逐条列出 |
| 必填节 | 按条目类型匹配小节标题（AST 取签名/可见性/是否有返回/是否抛异常 → 推出"应有节"） | 缺节 → 列出清单 |
| 链接可解析 | 相对路径与锚点解析 | 死链 → FAIL |
| Runbook 齐全 | 七件套小节存在性 | 缺一件 → FAIL |
| 禁止项扫描 | 超大代码块 / 日志粘贴 / TODO 标记 | 命中 → 提示（不直接 FAIL，需人判） |

> 设计要求：**能跑、能给出具体行号**、退出码可判定（0 = 通过）。不能给出定位的检查等于没有检查。

## 七、与 P008 的关系

P008 的反向写作（陌生库 → 文档体系）**复用同一份契约**：

- 阶段 1 写作：按本契约的条目模板写
- 阶段 3 审计：「完整性（条目级）」= 本契约的必填节检查；「真实性」= 实体存在率

**唯一差异**：反向写作多一层「覆盖」（inventory 每条都要有落点），那是 P008 特有的分母；契约本身两边通用。

## 八、落地顺序（建议）

1. 契约落成 skill（`doc-contract`），内容即本文件
2. `doc-lint` 最小版：实体存在性 + 必填节 + 链接（先支持 Python/TS，与 Q002 一致）
3. coding agent 提示词加一行引用 + 预审门里加一条「doc-lint 零违规」
4. coding-review 增加「跑 doc-lint 复核」的审查面
5. P008 阶段 1/3 直接调用同一工具
