# doc-from-zero · 框架全文（草案）

> 2026-10-19 立项讨论产物。**只是框架，未定稿**——待用户看完拍板后再决定是否进入设计。

## 一、要解决的问题

输入：一个陌生代码库（默认 100% 纯代码、无 git 历史、无文档，或文档极差）。
输出：一套能被第三方（人或其他 Agent）直接使用的文档体系。

三条硬要求：
1. **写全**——功能点一个不漏（可数、可审）
2. **不编造**——文档里说的每件事都能回指代码证据
3. **可跑**——照着文档能把系统从零跑起来

## 二、为什么 doc-init 这套不够

现有做法（skill）：①广度侦察产功能点索引 → ②子代理分批直出 → ③总览升级。

| 问题 | 后果 |
|------|------|
| 侦察与写作由同一批 agent 串行推进 | 探索成本 × 功能点数，**慢** |
| 「全不全」靠 agent 自评 | 无法审计，漏了就漏了 |
| 无实体真实性校验 | 幻觉 API/函数名无人拦截 |
| 写作串行 | 天然的并行工作被串起来做 |

## 三、四阶段框架

### 阶段 0 · 清单（inventory）——机械，不花模型时间

抽取来源（按可靠性排序）：

| 来源 | 得到什么 |
|------|----------|
| 依赖图（codegraph / AST） | 模块树、组件、入度为 0 的**入口点** |
| 入口扫描 | main / CLI 子命令 / HTTP 路由 / 事件处理器 / 公开导出 |
| 配置与清单 | 配置键、默认值、必需项（env/配置文件/schema） |
| 数据层 | 表结构 / 模型定义 / 迁移（若有） |
| 构建与运行 | 构建脚本、启动命令、镜像/编排文件 |
| 测试 | **测试即可执行规格**：用例名与断言的语义（不是照抄） |

产出 `inventory.md|json`：每条 = ID + 类型（入口/模块/配置/数据/行为）+ 位置（file:line）+ 状态（未覆盖/已覆盖）。
**这份清单是后续一切判定的分母。**

### 阶段 1 · 分层写作（并行）

- 按模块树切批，**自底向上**（先写被依赖的；DocAgent 消融证明顺序影响真实性）
- 每批一个 agent，上下文 = 本模块源码 + 依赖模块**已完成文档**（不是源码，省上下文）
- 跨模块实体：只建引用，不重复描述（CodeWiki 引用登记表）
- 复杂度超限：动态下派子模块

### 阶段 2 · 汇编

父层模块文档由子文档合成：架构总览、模块协作、数据流、使用指南、架构图。
**只合成不新增事实**——汇编层出现的每个新事实都必须有叶子证据，否则视为幻觉。

### 阶段 3 · 三查审计（确定性优先）

| 查什么 | 方法 | 判定 |
|--------|------|------|
| **覆盖** | inventory 每条 ↔ 文档章节逐条对账 | 缺一条 = 零覆盖（与 P007 Q007 覆盖矩阵同款） |
| **真实性** | 文档提到的实体（函数/类/端点/配置键）逐个回查代码 | 存在率 < 100% 即打回 |
| **可跑** | 照 Runbook 在干净环境从零 boot | 跑不起来 = 文档 FAIL |

可选第四查（人工/后续）：**有用性**——LLM 判官按"新人能否据此上手"打分（DocAgent 的做法）。

## 四、与 SOP-1（from-zero-to-mvp）的结构对照

| 维度 | SOP-1 规划→编码→测试 | SOP-2 doc-from-zero |
|------|----------------------|---------------------|
| 串并行 | 阶段串行，审查串行 | **写作可并行**（同层模块互不依赖） |
| 完成判据 | 树目标逐项对照实物 | **清单逐条对账** |
| 幻觉风险 | 低（代码要跑） | **高**（文档只被读）→ 需要真实性查 |
| 产出位置 | 黑板 plan tree + 项目工作区 | 待定（见 Q003） |

## 五、速度策略（针对用户反馈"慢"）

1. **清单位置前移**：把探索一次性做完，写作 agent 不做探索（这是最大的一块）
2. **并行写作**：同层模块并发，受控并发度（沿用渲染的 4 worker 经验）
3. **上下文只喂依赖文档**：拓扑序天然保证"依赖已写完"，避免每次重读源码
4. **审查批量化**：按批次审，不按文档篇审（减少审查轮次）
