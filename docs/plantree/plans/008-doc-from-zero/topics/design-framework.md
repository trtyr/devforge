# doc-from-zero · 框架全文（草案）

> 2026-10-19 立项讨论产物。**只是框架，未定稿**——待用户看完拍板后再决定是否进入设计。

## 一、要解决的问题

输入：一个陌生代码库（默认 100% 纯代码、无 git 历史、无文档，或文档极差）。
输出：一套能被第三方（人或其他 Agent）直接使用的文档体系。

三条硬要求：
1. **写全**——功能点一个不漏（可数、可审）
2. **不编造**——文档里说的每件事都能回指代码证据
3. **可跑**——照着文档能把系统从零跑起来

## 二、为什么 doc-init 这套不够

现有做法（skill）：①广度侦察产功能点索引 → ②子代理分批直出 → ③总览升级。

| 问题 | 后果 |
|------|------|
| 侦察与写作由同一批 agent 串行推进 | 探索成本 × 功能点数，**慢** |
| 「全不全」靠 agent 自评 | 无法审计，漏了就漏了 |
| 无实体真实性校验 | 幻觉 API/函数名无人拦截 |
| 写作串行 | 天然的并行工作被串起来做 |

## 三、Agent 编制：两类，就两类

> 沿用开发链（plan/coding/testing）的同一套骨架：**一个干活的 + 一个审查的**，循环推进，PASS 才落地。
> 下面「五阶段」不是五个 agent，而是**干活 agent 内部的五个步骤**；审查 agent 在检查点介入。

| profile | 干什么 | 供给 |
|---|---|---|
| **doc-agent**（干活） | 清单 → 勘察 → 解释 → 写作 → 汇编 | `codegraph` + `context7` MCP（与 coding-agent 同款）、写作类 skills |
| **doc-review**（审查） | 五项审计 + 跑 doc-lint，出 verdict + route | `codegraph` MCP（查实体存在性必须有） |

**循环**（与 coding SOP 同构）：

```
doc-agent 交一个单元（模块/条目批次）
   ↓
<doc-complete>unit-N + 落盘证据
   ↓
doc-review 审：跑 doc-lint + 五项审计
   ↓
PASS → 提交 + 下一单元        FAIL → <issues> 全量列 + <route> 回该阶段
```

- **审查角色不可省**：自己写自己审等于自证（GitLab playbook：约束要进门禁，不进提示词）。
- **审查只判不写**：审查 agent 给问题与证据，改由 doc-agent 做——否则文档会两极风格。
- **失败路由**（沿用 D002）：清单缺口→phase0、事实错→phase1、置信度标错→phase2、契约/链接/Runbook→phase3；route 缺失或非法保守回 phase3；协议违例上限复用 `MAX_PROTOCOL_VIOLATIONS = 3`。

> **codegraph 不是外部工具，是我们给 agent 的 MCP 配置**（`codegraph_mcp()`，stdio `codegraph serve --mcp`，`CODEGRAPH_TELEMETRY=0`）。沿用 decisions/013：**引擎侧预检 `init`，agent 不自行 init**；所有调用显式 `projectPath=<被 document 的项目>`（agent 的 cwd 是黑板）。

## 三·B · 节奏：四道门（2026-10-19 二次检索校准）

> 结论：**渐进式**是对的；"全写完再一次性审"是被点名的反模式（见 §五·E）。

```
门 0  清单 + 模块树 + 档位        ← 底座，最严；分母错则全错
        ↓ PASS 才开工写作
单元滚动  一批 = 审查官一轮读得完的量
        ↓ PASS 才 commit
汇编单元  总览 / 数据流 / Mermaid  ← 只合成不新增事实
        ↓
终审      全局覆盖对账 + 跨模块一致性 + 全量 doc-lint
```

### 什么叫一个"单元"

**单元 = 一次「提交 → 审查」能闭环的最小自洽块**，不是"一篇文档"也不是"整个项目"。

| 字段 | 内容 |
|---|---|
| 边界 | 模块树上的一个叶子模块（或同层无依赖的若干叶子合批） |
| 自带 | 该模块的事实记录 + 推断条目（带置信度）+ 已写好的 `docs/contexts/` 文件 |
| 前提 | 它依赖的模块**已通过审查**（拓扑序：DocAgent 消融乱序写真实性 94.64%→86.75%） |
| 交付 | `<doc-complete>unit-<id>` + **outcome 证据**（`git diff` + doc-lint 退出码 + `path:line` 清单） |
| 落地 | PASS → 一个 commit（一单元一提交，断了能续） |

### 三条硬约束（有实证，不是美学）

1. **批大小不按模块数拍死，按"审查官一轮真正读得完"定**。代码审查的实证锚点：100-300 行最佳、>400 行失控、>60 分钟判错率断崖（SmartBear/Cisco 2500 次审查）。模块大小差异大时，按数量拍批一定失真。
2. **检查点只认 outcome，不认自述**。agent 说"我查过了"不算；只认 `git diff`、doc-lint 退出码、实体回查结果。
3. **终审不可省**。只在跨模块才暴露的错误（重复描述、总览引用不存在的模块、全局覆盖缺口）会被所有单元门放行——粒度错配是已知失效模式。

### 为什么门 0 要单独审

清单是分母；分母漏项，后面的 100% 覆盖率就是自欺。三道闭包校验（入口可达 / 文件覆盖 / 符号覆盖）必须在写作开工前过审。GitHub 的 stacked PR 指南同理：**底座那层错了，上面每一层都会传染**。

### 单元粒度（修正 CodeWiki 的参数用法）

CodeWiki 的"叶子 ≤ 32K tokens"是**模块切分上限**，不是一次写作的上下文预算。RepoDoc 实测的姿势是：**文档单元按 4096 tokens 门槛聚类 + 图查询只取相关片段**（不灌整个文件）——省 85% token、快 3 倍。所以：

- 模块树切分：叶子 ≤ 32K（CodeWiki）
- 单次写作上下文：≈4K 代码片段（RepoDoc），不够再用图查询补

## 四、五阶段（doc-agent 的内部步骤，事实 / 推断分离）

> 结构借 Reversa（勘察→挖掘→解释→生成→审查）＋ CodeWiki（模块树/汇编）＋ DocAgent（条目严谨度），三者合并为下面的骨架。

### 阶段 0 · 清单（inventory）——机械优先，codegraph 为主

**算法在 codegraph 里，不在我们手里**：它已经把 AST → 依赖图 → SCC 缩点 → 拓扑排序 → 入口点识别这条链做完了（20+ 语言、router 识别 17 个框架）。所以阶段 0 的动作是：

1. **引擎侧预检**：有 `.codegraph/` 就直接用；没有则**引擎先 `codegraph init`**（decisions/013：agent 不自行 init，免得每个单元都重建索引）
2. **agent 调 MCP 建图**：`codegraph files` / `query` / `explore` / `node`，显式 `projectPath=<目标项目>`
   - 入口点来源：入度为 0 的符号 + **框架 router 识别**（HTTP 路由）+ CLI 入口 + 公开导出
   - 模块树：按目录/模块边界切，**叶子 ≤ 32K tokens**（CodeWiki 实测量）
   - 叶子仍超限时：按**圈复杂度 / 嵌套深度 / 语义多样性 / 上下文占用**四类可计算判据下派子模块，**深度上限 3 层**
3. **机械补漏（codegraph 不管的部分）**：配置键（env/配置文件/schema）、构建与启动命令、数据层（表/模型/迁移）、测试用例名与断言语义
4. **闭包校验（引擎侧工具，不由 agent 自证）**：入口可达闭包 / 文件覆盖 / 符号覆盖——三道都过，清单才能当分母（D002）

抽取来源（按可靠性排序）：

| 来源 | 得到什么 |
|------|----------|
| codegraph MCP | 模块树、组件、入度为 0 的**入口点**、调用关系、影响面 |
| 框架 router 识别 | HTTP 路由 → handler 对应关系（17 个框架：Rails/Spring/Play/Gin/Express/Next/Axum…） |
| 配置与清单 | 配置键、默认值、必需项（env/配置文件/schema） |
| 数据层 | 表结构 / 模型定义 / 迁移（若有） |
| 构建与运行 | 构建脚本、启动命令、镜像/编排文件 |
| 测试 | **测试即可执行规格**：用例名与断言的语义（不是照抄） |
| **codegraph 不支持的语言** | 登记为缺口，**不假装支持**（D004） |

产出 `inventory.md|json`：每条 = ID + 类型（入口/模块/配置/数据/行为）+ 位置（file:line）+ 状态（未覆盖/已覆盖）。
**这份清单是后续一切判定的分母。** 入口点条目要标 `kind=entry`——写作时优先。

同时定一个 **`doc_level`（三档，借 Reversa）**：

| 档位 | 写什么 | 适用 |
|------|--------|------|
| **essential** | 入口点清单 + 运行手册 + 顶层架构 | 只需“能跑、能接” |
| **complete**（默认） | + 每模块行为语义、配置项、错误码、数据模型 | 接手维护 |
| **detailed** | + 算法/状态机/权限矩阵/回溯 ADR | 长期演进、合规审计 |

> “写全”必须先定义到档位——否则“全”没有终点。

### 阶段 1 · 勘察（只记事实，不解释）

- **一模块一会话**（Reversa 的上下文纪律：大项目一次全分析会烧光上下文、质量崩）；单次上下文≈4K 代码片段，不够用图查询补（§三·B）
- 产出只描述“有什么”：函数/数据结构/控制流/外部依赖/公开输出
- **严禁在此阶段写“为什么”**——解释属于阶段 2，两者混写就无法区分事实与猜测
- 可并行的只是**同层无依赖的模块**，受控并发

### 阶段 2 · 解释（推断，必须标置信度）

对勘察结果做归因与建模：业务规则、状态机、权限矩阵、模块职责边界。

**置信度标记（强强制，每个断言一行一个）**：

| 标 | 含义 | 判定要求 |
|---|---|---|
| 🟢 CONFIRMED | 代码/运行输出直接可见 | 能给出 `path:line` 或可重放命令 |
| 🟡 INFERRED | 合理推断 | 写出依据（命名/结构/行为观察） |
| 🔴 GAP | 无法从代码得知 | 转成问题，交调用方（呼应“验收归调用方”） |

> **无 git 的硬约束**：Reversa 的 Detective 靠 git 历史回溯“为什么这么设计”；**无 git 时这条路径不存在**，只能靠命名/数据结构/运行时行为，**全部计 🟡**。

### 阶段 3 · 生成 / 汇编

- 按 `doc_level` 生成条目文档，模板见 `doc-contract.md`
- 父层由子文档合成：架构总览、模块协作、数据流、使用指南、架构图
- **两条硬约束**：①只合成不新增事实；②上层断言必须可追溯到叶子证据（子错会向上传染）
- 专用来源 agent（可选）：**DB schema agent**（DDL/迁移 → 数据字典）、**UI agent**（截图/CSS → 界面说明）

### 阶段 0·补 · inventory 自身的完备性校验（防循环自证）

> 风险：如果事实清单本身就漏了模块，覆盖率照样 100%，永远发现不了。分母必须自己可验。

三道闭合校验（机械，不靠模型）：

| 校验 | 判据 | 不合格的含义 |
|---|---|---|
| **可达闭包** | 从入口点出发沿依赖图能到达的模块 = 清单模块集合 | 有不可达孤儿代码 → 要么是死代码（登记），要么漏了入口 |
| **文件覆盖** | 每个源文件至少属于一个模块 | 有文件没人认领 → 清单漏了 |
| **符号覆盖** | 每个公开符号（导出函数/类/端点/配置键）至少出现在一个条目里 | 有公开能力没进清单 → “写全”的分母漏了 |

三项都过，清单才可以当分母。**否则覆盖率数字无意义。**

### 阶段 4 · 审计（确定性优先）

| 查什么 | 方法 | 判定 |
|--------|------|------|
| **覆盖** | inventory 每条 ↔ 文档章节逐条对账 | 缺一条 = 零覆盖 |
| **完整性（条目级）** | **AST 机械判定**：按条目类型推必填节，得分 = 实有/应有 | 缺节即列出 |
| **真实性** | 文档提到的实体逐个回查代码 | 存在率 < 100% 即打回 |
| **置信度诚实性** | 抽查标 🟢 的断言：能否真给出 `path:line`/重放命令 | 标错绿灯 = **FAIL**（最严重） |
| **可跑** | 照 Runbook 从零 boot | 跑不起来 = FAIL |

可选：**有用性**——LLM 判官打分，仅作参考（判官独立性不足，不能作为唯一依据）。

> 审计结束时产出一份 `gaps.md`：所有 🔴 条目转成待回答的问题，交调用方/人。

### 阶段 4·补 · 失败路由与协议映射（不定义就会卡死）

**打回必须回到“对的那一层”**，否则改文档永远改不好：

| FAIL 原因 | 路由目标 | 判据 |
|---|---|---|
| 清单不完备（闭包/文件/符号校验不过） | **回阶段 0** | 机械校验失败 |
| 事实记录错了/漏了 | **回阶段 1**（重勘察该模块） | 审计给出反例：文档说 X，代码是 Y |
| 推断标错置信度 | **回阶段 2** | 标 🟢 但给不出 path:line |
| 条目缺节 / 链接死 / Runbook 不全 | **回阶段 3**（局部返工） | 契约检查 |
| 汇编层凭空造事实 | **回阶段 3**（汇编段） | 无法溯源到叶子 |

**协议映射**（跟现有 SOP 机制对齐）：

- 每个阶段结束发 `<stage-complete>N</stage-complete>`（沿用 P005/P007 同一实现）
- 审计输出 `<doc-verdict>PASS|FAIL</doc-verdict>` + `<route>phase0|phase1|phase2|phase3|finish</route>`
- **缺 route 或值非法 → 保守按 `phase3` 处理**（与 P007 "宁退回不滥升级"同口径：能局部改就不重跑全局）
- 连续协议违例上限复用 P007 的 `MAX_PROTOCOL_VIOLATIONS = 3`

### 检查点与续跑（长跑必需）

这轮 test_19 跑 4 小时的经验：**中途断了不能从头再来**。

- 状态文件：`<doc-root>/.docgen/state.json`（清单版本、已完成模块、审计结果、轮次）
- 粒度：**一模块一提交**（已完成的模块不重跑）；清单变了才全量失效
- 幂等：同输入重跑输出一致；`--only <module>` 支持单点重派

### 写作顺序与上下文（保留 CodeWiki/DocAgent 的两条）

- **自底向上**（先写被依赖的；DocAgent 消融：乱序写真实性 94.64%→86.75%）
- 每个叶子 agent 手里四样东西：本模块源码 / 整棵模块树 / 文档工作区读写 / 依赖图遍历
- 跨模块实体只建引用，不重复描述

## 四·补、与 SOP-1（from-zero-to-mvp）的结构对照

| 维度 | SOP-1 规划→编码→测试 | SOP-2 doc-from-zero |
|------|----------------------|---------------------|
| 串并行 | 阶段串行，审查串行 | **写作可并行**（同层模块互不依赖） |
| 完成判据 | 树目标逐项对照实物 | **清单逐条对账** |
| 幻觉风险 | 低（代码要跑） | **高**（文档只被读）→ 需要真实性查 |
| 产出位置 | 黑板 plan tree + 项目工作区 | 待定（见 Q003） |

## 五、速度策略（针对用户反馈"慢"）

1. **清单位置前移**：把探索一次性做完，写作 agent 不做探索（这是最大的一块）
2. **并行写作**：同层模块并发，受控并发度（沿用渲染的 4 worker 经验）
3. **上下文只喂依赖文档**：拓扑序天然保证"依赖已写完"，避免每次重读源码
4. **审查批量化**：按批次审，不按文档篇审（减少审查轮次）
5. **必须记录耗时与成本**：CodeWiki 全文**没报运行时间/成本**（只报质量分），这是它的空白，也是我们最痛的点——每次跑完落盘：模块数 / 并行度 / 墙钟 / 每模块轮数 / token 消耗。没有这个数据，优化全靠玄学。

## 五·B · CodeWiki 精读结论（2026-10-19）

**可直接借用**：SCC 缩点 + 拓扑序；入度 0 = 入口点；叶子 32K / 下派 3 层；四类下派判据；跨模块引用登记；父文档由子文档合成。

**不可照搬**：

| 它的做法 | 为什么不适用 | 我们的替代 |
|---|---|---|
| 用**官方文档**反生成分层 rubric 来打分 | 我们的场景恰好没有官方文档（这是前提，不是巧合） | 自造分母：inventory 覆盖率 + 实体存在率 |
| 三厂商判官投票 | 模型池独立票源不足 | 机械判定为主，判官只做参考分 |
| 未报耗时/成本 | 正好是我们最关心的 | 每次跑落耗时账 |
| C/C++ 支持弱（53.24% vs 脚本语言 79.14%） | 它自己承认：指针/模板这些底层构造本身就是架构 | 首版只承诺脚本语言（Q002） |

## 五·C · DocAgent 精读结论（2026-10-19）

**它解决的三种烂文档**：缺信息（只写 summary）/ 没用（不复述"为什么"与使用场景）/ **编造（凭空引用不存在的组件）**。

**架构**：Navigator（AST → 依赖图 → Tarjan 缩点 → 拓扑序；**方法先于所在类**）+ 五角色协作：

| 角色 | 职责 |
|---|---|
| Reader | 判断"写好它还需要什么"，输出结构化请求：内部依赖 / **调用点**（暴露用途）/ 外部知识 |
| Searcher | 拿请求去捞：源码、已有文档、调用点、依赖追踪、类层次；**与 Reader 可多轮往返**，探索成本只花在需要的地方 |
| Writer | 按组件类型套模板（函数：摘要/描述/Args/Returns/Raises/示例；类：初始化示例/构造参数/公开属性） |
| Verifier | 打分＋**两条反馈路径**：格式问题→Writer；缺上下文→Reader 再捞一轮 |
| Orchestrator | 控循环＋**自适应截断**（超阈值时从最大段落尾部削，保结构） |

**三维评估与实测**：

| 维度 | 算法 | DA-GPT / Chat-GPT / FIM |
|---|---|---|
| 完整性 | **AST 机械**：按签名/函数体/可见性推必填节，得分=实有/应有 | **0.934** / 0.815 / 0.314 |
| 有用性 | LLM 判官 5 分制，**按段落分开评** | **3.88** / 2.95 / 1.51 |
| 真实性 | 抽实体 → 依赖图查存在 → **存在率** | **95.74%** / 61.10% / **45.04%** |

**消融（拓扑序 → 随机序）**：有用性 3.69→3.44；真实性 94.64%→86.75%。原因：拓扑序保证"依赖已有现成文档"，上下文增量积累。
（原文小细节：正文表 2 的 3.88 与消融 3.69 不矛盾——消融在随机 50 个组件子集上做。）

**它的边界（对 P008 最关键的定位）**：CodeWiki 对比表里 DocAgent = **✗ Repo-Level Doc**，它产出的是**逐组件条目**，不做仓库级分层汇编。

> **所以 P008 的正确组合**：**CodeWiki 管结构**（模块树/层级汇编/架构图/跨模块引用），**DocAgent 管条目**（单个组件写得多完整、多准、有没有编造）。

**直接采纳的三条**：① 完整性改机械判定（已入阶段 3 第二查）；② 真实性阈值 100%，不合格逐条列 finding；③ 写作前先拓扑序 + 依赖已有文档（已入阶段 1）。

**它也没解决**：只有 Python；静态分析为主（动态行为抓不到）；幻觉仍存；**同样未报耗时/成本**。

## 五·D · Reversa 精读结论（2026-10-19）

【Reversa 分析流水线】(https://sandeco.github.io/reversa/pipeline/)：把遗留系统变成**可执行规格**的五阶段 agent 流水。它是本次检索中**与 P008 需求最贴合**的工程实现。

| 阶段 | Agent | 产出 | 关键纪律 |
|---|---|---|---|
| 1 侦察 | Scout | inventory.md / dependencies.md / **surface.json**（结构化，用于把后续拆成“每模块一任务”） | 先定 `doc_level`（essential/complete/detailed） |
| 2 挖掘 | Archaeologist | code-analysis.md / data-dictionary.md / 每模块流程图 / modules.json | **一模块一会话**；**只记录不下判断** |
| 3 解释 | Detective + Architect | domain.md / state-machines.md / permissions.md / 回溯 ADR / C4 三层图 / ERD | 侦探靠 **git 历史**推“为何”；无 git 时只能全计 🟡 |
| 4 生成 | Writer | 每单元 requirements/design/tasks + OpenAPI + 用户故事 + 追溯矩阵 | **每句标 🟢CONFIRMED / 🟡INFERRED / 🔴GAP**；一次一文件、等人确认 |
| 5 审查 | Reviewer | questions.md / confidence-report.md / gaps.md | 专查“**标了 🟢 其实是推断**”；🔴 缺口转问题交人 |

**独立 Agent**：Visor（截图）、Data Master（DDL/迁移/ORM）、Design System（CSS/主题）、Soul Extractor（一句话执行摘要）。

**我们对它的取舍**：

| 它有什么 | 我们怎么办 |
|---|---|
| 🟢🟡🔴 置信度 | **全量采纳**，并加成审计项（标错绿灯 = FAIL） |
| 事实（挖掘）/推断（解释）分阶段、分 agent | **全量采纳**，已重构为五阶段 |
| doc_level 三档 | **采纳**，默认 complete |
| 一模块一会话 | **采纳**，作为上下文纪律 |
| 靠 git 历史回溯 ADR | **不可用（无 git）** → 改用命名/数据结构/运行时行为，全部标 🟡 |
| Writer 一次一文件等人确认 | **不采纳**（我们是全自动 SOP）→ 改为整批生成后统一审 |
| 专用来源 agent | **选采**：先做 DB schema，UI 留后 |

**特征定位（“怎么挖功能点”）的学术骨架**：
- [A Survey of Feature Location Techniques](https://www.cs.toronto.edu/~chechik/pubs/locationsurvey12.pdf)：静态（依赖/调用图）/ 动态（执行轨迹）/ IR（标识符与注释相似度）/ 混合
- 我们的组合：**静态优先（入口点+依赖图）→ 可跑则补动态（真实调用链）→ IR 只当命名探测**
- 背景数据：专业开发者**最多 70% 的时间花在程序理解上**（Xia et al., TSE 2018）——这就是这个 SOP 存在的理由

## 五·E · 渐进式节奏的检索结论（2026-10-19）

四个来源，结论互相印证。

### ① 增量验证（[agentpatterns.ai](https://agentpatterns.ai/verification/incremental-verification/)）

- **反模式**："write everything, then review"——错误在整个产物里复合
- 正确姿势：每完成一个有意义的单元就验，错误离源头越近修复越便宜
- **检查点不能读 agent 自述**：必须配 outcome 检查（`git diff` / 构建退出码 / 测试输出）；"只读自述的检查点不算检查点"
- 三条反噬条件：①单元太小（固定开销吞掉收益）②检查者比生成者弱（无约束 LLM 裁判不算）③**粒度错配**（只在跨组件暴露的错误，单元门全放行）
- 保存已知良好状态（commit/快照）再来一批，把爆炸半径限制在一个检查点区间

### ② SmartBear / Cisco 代码审查实证（2500 次审查，10 个月）

- **规模**：100-300 行最佳，>400 行"审查者被淹没，缺陷抓不到"
- **时长**：>60 分钟缺陷发现率断崖，>90 分钟显著下降
- **速率**：<300 行/小时最佳；>450 行/小时时 87% 的审查低于平均缺陷密度
- **缺陷率恒定**约 15 个/小时 → 小批量才堆得出高缺陷密度
- **交审前作者预注释（被迫自审）→ 缺陷密度极低**（有注释的审查缺陷密度从不超过 30/kLOC，且多数为 0）

> 对我们的映射：审查一轮的量要"读得完"（≈一次 30-60 分钟），而不是按模块数量硬拍；doc-agent 交审前自跑 doc-lint + 回写证据，就相当于"作者预注释"。

### ③ GitHub 官方 stacked PR 指南（专门针对 AI 生成的大量代码）

- **先设计栈再生成**：每层是一个可独立审完的内聚变更；"如果一层需要长描述才能审，它就太大了"
- **按依赖顺序排**：基础层在下，依赖它的在上
- **底层先审**："底座那层的错误会传播到上面每一条分支"
- **修在它所属的那一层**，不要在错的层改（改错层会让上层全乱）
- 合并自底向上，每层通过即合，不必等整栈

### ④ RepoDoc（[arXiv 2604.26523](https://arxiv.org/html/2604.26523v1)）——文档全生命周期 + 增量

24 仓 / 8 语言 / 小到 <10K LOC 大到 >100K LOC 实测：

| 维度 | 结果 |
|---|---|
| 生成速度 | 1242s，比 CodeWiki 快 **3×**、比 RepoAgent 快 **15×** |
| token | 比 CodeWiki **-85%**（$0.39/仓） |
| 增量更新 | 时间 **-73%**、token **-77%**、**更新召回 97%**（全量重生成只有 88%） |
| API 覆盖率 | 比 CodeWiki **+32.5%** |
| 图 | 自动生成 Mermaid（支持 D005 的做法） |

它的三个做法直接可用：

1. **按功能内聚聚类，不按物理目录**：顶层 K=5、子层 K=3、**阈值 4096 tokens**
2. **图查询只取相关片段**（不灌整个文件）→ 省 85% token 的主因
3. **增量更新四步**：变更检测（commit diff + AST 定位实体）→ **语义影响传播**（在图上双向遍历找受影响模块）→ 选择性重生成 → 一致性校验（链接/图引用/模块文档是否反映子部件）

它同时批评了两家：CodeWiki 按"物理大小"切模块（不是功能内聚）、父节点吸收全部子文档导致 token 指数膨胀；RepoAgent 按文件结构组织 + 只做文件级增量（无语义传播），且 18629s / 仓。

### 对本 SOP 的净影响

| 改什么 | 原来 | 现在 |
|---|---|---|
| 节奏 | "全写完→审" 或 "每模块一审" 两端 | **四道门**（底座 / 单元滚动 / 汇编 / 终审） |
| 批大小 | 3-5 个模块 | **审查官一轮读得完的量**（不写死数字） |
