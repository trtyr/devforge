# doc-from-zero · 决策记录

## D001 · 文档体系唯一权威 = 本 plan；`doc-init` skill 退役

- **决策**（用户拍板 2026-10-19 20:50）：`doc-init` skill 以后退役，不再维护；`doc-from-zero` SOP 是"从零写文档"的唯一权威，文档 schema 以 `topics/doc-contract.md` 为准。
- **为什么**：两套 schema 并存会导致双权威漂移；用户明确不按旧 skill 的约束走。
- **后果**：
  - `docs/contexts/` 六节格式、`<!-- doc:start:slug -->` 标记契约**不再作为约束**（可以吸收其思想，但不强制沿用）
  - 旧 skill 的 `docs-update`（增量对齐）链条需要重新定义（见 Q013）
  - 现有仓库里已按旧格式产出的文档不强制迁移

## D002 · 吸收 doc-init 的工程教训为红线（不吸收就会重踩）

- **决策**：虽然 schema 作废，但 `doc-init` 在实践中踩出来的下列教训**直接转为本 SOP 的红线**：
  1. **证据下限**：每条事实性断言必须有 `path:line`（旧 skill 的硬性下限，失效点在于没和"覆盖"绑定）
  2. **防伪标记**：任何"我已完成"的标记必须是**独占一行 + 真实正文**；散文里罗列标记视为撒谎（旧 skill 被弱模型骗过票）
  3. **编号/路径稳定**：文档编号按全量清单预先分配，部分失败重跑时**不许漂移**
  4. **幂等重跑**：已产出的单元跳过，支持 `--only <unit>` 单点重派
  5. **只读被 document 的仓库**：除文档产物目录外不改任何源码
  6. **任务书回显不算产物**：中间产物（任务书、审计编号、重试记录）不进终稿
- **为什么**：这些是拿真实失败换来的，schema 换了但失败模式不变。
- **后果**：审计里加"防伪"一条（标记作弊检测），与 P007 的协议违例处理同款思路。

## D003 · 产物落点 = 目标项目内 `docs/contexts/`

- **决策**（用户拍板 2026-10-19 20:54）：所有文档直接落在**被 document 的项目**里——`<项目>/docs/contexts/`。
- **为什么**：文档的价值是跟着代码走；放在系统侧黑板别人拿不到。
- **后果**：① 只读红线要留一个例外（`docs/contexts/` 可写，其余源码不许动）；② 项目目录不可写时（只读挂载）需显式报错而不是静默改道。

## D004 · 多语言走 codegraph，不自建 AST 抽取器

- **决策**（用户拍板）：语言覆盖以 **codegraph** 为准（20+ 语言全支持：TS/JS/ArkTS/Python/Go/Rust/Java/C#/VB.NET/PHP/Ruby/C/C++/Swift/Kotlin/Scala/Dart/Lua/R/Nix/Erlang/COBOL/Solidity/Terraform 等），并直接使用它的**框架路由识别**（17 个框架）作为入口点来源之一。
- **为什么**：自建多语言解析是重复造轮子；codegraph 的图已验证过覆盖度（TS/JS 95.8%、Python 100%、Go 96.6%、Java 93.3%）。
- **后果**：① 清单抽取器只做"codegraph 查询 + 结构化归一"，不写 parser；② **未覆盖语言 = 显式降级**（登记为缺口，不许假装支持）；③ codegraph 索引是前置（未初始化先 `codegraph init`）。

## D005 · 画图：只产 Mermaid 源码，不渲染图片

- **决策**：架构图/数据流图**以 Mermaid 代码块形式**写进文档；不生成 PNG/SVG。
- **为什么**：旧实践里"存根图/宣告图"渲染失败率高（2026-10-12 拍板不画图的直接原因）；Mermaid 源是文本，可 diff、可校验、可被任何消费者渲染，失败面小得多。
- **后果**：审计只校验"图源码可解析 + 引用的节点在清单里存在"，不校验渲染效果。

## D006 · 置信度：正文极简标记 + 旁挂证据表

- **决策**：终稿正文里，推断性结论用一句 `（推断：依据xxx）` 标注；完整三色清单（🟢/🟡/🔴 + 证据指针）落在 `docs/contexts/_meta/confidence.md`，与正文逐条对应。
- **为什么**：正文保持可读（读者不需要看满屏符号）；审计要的是可追溯的证据表——两者分开，各司其职。
- **后果**：审计查两件事——① 侧车表里每条 🟢 必须给得出 `path:line` 或重放命令；② 正文里出现"（推断）"但侧车标 🟢 的，判标错。

## D007 · 默认文档档位 = complete

- **决策**：`doc_level` 默认 `complete`；API 参数可覆盖为 `essential` / `detailed`。
- **为什么**：essential 只够"能跑能接"，detailed 成本高；complete 是接手维护的甜点。

## D008 · doc-lint = devforge 侧本地脚本

- **决策**：检查工具由我们在 devforge 侧实现，作用于任意目标工作区；**不往被 document 的仓库里塞脚本**（除 `docs/contexts/` 外不写文件）。
- **为什么**：保持目标仓库干净；工具随系统升级，不用在每个项目里维护副本。

## D009 · 双 Agent 编制：doc-agent（干活）+ doc-review（审查）

- **决策**（用户拍板 2026-10-19 20:56）：沿用开发链的极简架构——**两类 Agent**：一个写文档的、一个检查文档的。五个阶段是**干活 agent 的内部步骤**，不是五个 agent。
- **供给**：doc-agent 拿 `codegraph` + `context7` MCP（与 coding-agent 同款配置）；doc-review 拿 `codegraph`（查实体存在性必须有）。
- **为什么**：① 自己写自己审 = 自证（GitLab playbook：约束要进门禁）；② 每多一个角色就多一份提示词漂移与上下文传递成本；③ 开发链已验证同一套循环（stage-verdict + route + issues 全量）能跑通。
- **后果**：审查只判不写（改由 doc-agent 做，避免风格两极）；失败路由复用 D002 的 route 表；协议违例上限 `MAX_PROTOCOL_VIOLATIONS = 3`。

## D010 · 节奏 = 四道门（2026-10-19 二次检索校准）

- **决策**：并非"全写完再一次性审"，也不是"每模块一审"；采用四道门：

  ```
  门 0  清单 + 模块树 + 档位（底座，最严）
    ↓ PASS 才开工
  单元滚动（一批 = 审查官一轮读得完的量）
    ↓ PASS 才 commit
  汇编单元（总览/数据流/Mermaid，只合成不新增事实）
    ↓
  终审（全局覆盖对账 + 跨模块一致性 + 全量 doc-lint）
  ```

- **三条硬约束**：① **批大小不按模块数拍死**，按审查阅读预算定（代码审查实证：100-300 行最佳、>400 行失控、>60 分钟判错率断崖、作者预注释则缺陷密度极低）；② **检查点只认 outcome**（`git diff` / doc-lint 退码 / 实体回查），不认 agent 自述；③ **终审不可省**（跨模块重复与全局覆盖只在最后暴露——粒度错配）。
- **单元粒度修正**：CodeWiki 的"叶子 ≤32K"是模块切分上限；**单次写作上下文 ≈4K 代码片段**（RepoDoc 实测），不够用图查询补。
- **依据**：agentpatterns.ai 的增量验证（点名 write-then-review 为反模式、检查者须强于生成者）；SmartBear/Cisco 2500 次审查实证；GitHub stacked PR 指南（底座先审、错层不修）；RepoDoc arXiv 2604.26523（4096-token 聚类、图查询取片段、增量召回 97%）。
- **后果**：每单元必须一提交（断点续跑）；门 0 不过则不进写作；五阶段的「阶段 4 审计」在编制上拆成“单元审”与“终审”两个时机，共用同一个 doc-review profile。

## D011 · 术语一致性：不另立词表，用「清单视图 + 引用 ID」

- **决策**（Q004，助手定 2026-10-19）：**不新增一份人工维护的 glossary**。术语统一靠两件机制：
  1. **清单即词表**：实体在 inventory 里带 `canonical_name` + `aliases`；词表是清单的一个**自动导出视图**（`glossary.md`），不手写、不单独审。
  2. **写作引用 ID**：文档首次提到某实体必须用清单里的规范名，别名必须已在清单登记。
- **汇编/终审校验（机械）**：同一实体在全文是否出现多个名称；文档里出现的名称是否都在清单里（不在 = 幽灵实体，直接 FAIL）。
- **为什么**：多一份人工词表 = 多一个会漂移的权威；而"清单 + 引用 ID"在实体存在性检查里已经免费得到了。CodeWiki 的全局引用登记表也能直接借用（跨模块只建引用不重复描述）。

## D012 · doc-review 供给 + doc-lint 由引擎跑

- **决策**（Q005，助手定 2026-10-19）：
  - doc-review 给 **codegraph MCP**（查实体存在性必须有），**不给** context7（它不需要外部库文档）、不给写作类 skills；`thinking_level = medium`（同其他 review profile）。
  - **doc-lint 不由 agent 跑，由引擎在交审前跑**，结果作为审查输入注入。agent 拿到的是确定性报告（哪些行、什么违例），不是"你自己查查"。
- **为什么**：① 检查者必须比生成者可靠（agentpatterns）——确定性脚本比 LLM 自己扫更可靠；② 省往返（审查官不用再跑一轮工具）；③ 防跳过（agent 无法"忘了跑 lint"）。
- **后果**：agent 交审时仍要附 `git diff` 与自检证据（作者预注释，SmartBear 实证能降缺陷密度），但**lint 退码是引擎盖的章**，不是自述。

## D013 · 完成判据：两层"100%"，不许静默缺口

- **决策**（Q006，助手定 2026-10-19）：完成 = 四条同时成立：
  1. **清单内覆盖 100%**——该 `doc_level` 要求覆盖的条目集合，一条不能缺（缺即 FAIL）
  2. **清单外缺口全部登记**——codegraph 不支持的语言 / 生成代码 / 二进制资源 / 无行为可写，均需在 `gaps.md` 写原因与影响面（静默缺口 = FAIL）
  3. **真实性 100%**——幽灵实体零容忍
  4. **可跑**——Runbook 从零 boot 成功
- **口径**：叫"**声明性完整**"——不是声称"这仓库全写完了"，而是"这仓库有什么我们说清了，包括我们没写的那部分"。
- **为什么不分高下**：只要求"覆盖率 100%"而不要求登记缺口，等于允许分母自己作弊（D002 三道闭包同源问题）；反过来只要求"登记缺口"不要求覆盖 100%，清单就失去意义。两者必须同时硬。

## D014 · 必填节：分级但分级表固定，不适用必须写 N/A

- **决策**（Q008，助手定 2026-10-19）：必填节**按条目类型定**，不由 agent 自判轻重：

  | 条目类型 | 必填节 | 缺节 |
  |---|---|---|
  | 入口点 | 用途/输入/输出/错误/示例 | FAIL |
  | 公开函数 | 摘要/行为语义/参数/返回/异常 | FAIL |
  | 公开类/接口 | 职责/初始化/公开成员/生命周期 | FAIL |
  | 配置项 | 名称/类型/默认值/取值范围/影响 | FAIL |
  | 数据模型 | 字段/类型/约束/关系 | FAIL |
  | 错误码 | 码值/触发条件/处理建议 | FAIL |
  | 内部/私有符号 | 摘要+行为语义 | 只记 finding |

- **N/A 规则**：确实不适用时必须写 `N/A` 并给理由（如"无参数"）——**省略不等于不适用**，否则"懒得写"和"真没有"无法机械区分。缺节且无 N/A = 缺节。
- **为什么分级**：一刀切"缺就 FAIL"会把内部函数逼成凑字；一刀切"分级但由 agent 判"则必然自洩。分级表进契约、进 lint 配置，才是机械可判的。

## D015 · 增量模式：内置同一道 SOP，不另开链

- **决策**：增量 = 本 SOP 的一个运行模式 `--update <base-commit>`（或 API 参数），**不新建第四条链**。
- **流程**：变更检测（diff + AST 定位实体）→ 语义影响传播（codegraph 双向遍历）→ 选择性重生成（只动受影响单元）→ 一致性校验（链接/图/父文档）。
- **为什么**：① RepoDoc 证明增量就是同一管线的缩范围运行；② 新开链 = 重写四道门、清单、契约，必然漂移；③ 状态文件与检查点天然复用。
- **后果**：`--update` 模式下门 0 只重算受影响模块的清单条目，不冻结全量。

## D016 · 产物目录与状态文件位置

- **决策**（修正 D002 的 `.docgen/state.json` 路径）：状态与元数据全部进 `docs/contexts/_meta/`，**不在项目根额外建目录**——因为只读红线只给 `docs/contexts/` 开口子。
- **2026-10-20 修正（plan 010 D001）**：**检查点不属于产物**——`state.json` 搬到黑板 `plans/<project>/<task>/doc-from-zero/state.json`（按 project/task/SOP 三级分文件）；`_meta/` 只留清单/词表/词库/审查记录/账单。理由：清产物（重生成、手滑、换档位）不该等于丢断点，且运行状态寄居产物目录会被误认为交付物。

```
<项目>/
└─ docs/contexts/
   ├─ README.md              总览（汇编产物）
   ├─ 01-architecture.md     架构（含 Mermaid）
   ├─ 02-dataflow.md         数据流（含 Mermaid）
   ├─ 10-runbook.md          运行手册（七件套）
   ├─ <module>/             模块文档（按模块树路径，一模块一目录/文件）
   └─ _meta/
      ├─ inventory.json     清单（分母，条目带 canonical_name/aliases/kind/evidence）
      ├─ glossary.md       清单导出的词表（自动生成，不手改）
      ├─ confidence.md     置信度三色证据表（D006）
      ├─ gaps.md           🔴 缺口与未覆盖登记（D013）
      ├─ state.json        检查点/幂等续跑（D002，替代项目根 .docgen/）——**已迁出**，见 D016 的 2026-10-20 修正
      └─ runs/<run-id>/    每次运行的耗时/token/模块数账单（§五·5）
```

- **为什么 `_meta/` 下划线开头**：文档阅读者一眼知道这些不是正文；lint 不对它查必填节。
- **例外**：项目仓库本身有 `docs/` 习惯目录时不迁移旧内容，新体系只占 `docs/contexts/`。

## D017 · 执行模型：串行滚动，不做并行编排

- **决策**：P008 按现有**串行 guard** 跑（一次一个 run），单元严格按拓扑序推进；**不做多单元并发**。
- **分批规则**：同层无依赖且合起来仍在审查阅读预算内的叶子可以合为一批；超预算就拆批。
- **超大仓（>100K LOC）**：先 `doc_level=essential` 粗跑一遍（覆盖入口点 + Runbook + 顶层架构），再按需对热点模块升级到 complete（`--only <module>`）。理由：RepoDoc 实测大仓全量重生成代价最高；分档可让“能跑”先交付。
- **为什么不做并发**：P004 并发未建；文档单元之间有强拓扑依赖，并发收益小于冲突成本。

## D019 · UI/可视化文档：MVP 不做截图代理

- **决策**：MVP 不引入截图/浏览器代理；前端相关条目只产 **组件树 / 路由表 / 状态流 / Mermaid 组件图**（均由 codegraph + 配置文件可得）。
- **理由**：截图需要浏览器与可控种子数据，成本高且不可机械判定；先把可确定的部分做对。
- **后果**：UI 视觉细节写入 `gaps.md`（“未覆盖：视觉布局，需人工补充”），不假装写了。

## D020 · 单元编号与协议命名

- **单元 ID**：`<模块路径>` 归一化（`/`→`-`）+ 预分配序号，如 `unit-core-auth-07`；编号在门 0 一次性分配、**不随局部重跑漂移**（D002）。
- **协议块**（与 P005/P007 同形）：
  - 干活：`<doc-complete>unit-core-auth-07</doc-complete>`（单元完成）
  - 审查：`<doc-verdict>PASS|FAIL</doc-verdict>` + `<route>phase0|phase1|phase2|phase3|finish</route>` + `<issues>`（FAIL 时全量列）
  - 缺/非法 route → 保守 `phase3`；协议违例上限 `MAX_PROTOCOL_VIOLATIONS = 3`。
- **SOP 名**：`doc-from-zero`（与 `planning`/`coding`/`testing` 同款注册，触发 `start {"sop":"doc-from-zero"}`）。
