# Decisions — P004

稳定决策记录。只记「选了什么 + 为什么 + 后果」。

---

## 001 · 项目-本地关系全手动指定

- **决策**：项目与本地建立关系一律用户手动指定——从 0 新项目：手动指定本地创建位置；已有项目：手动指定路径登记入系统。无自动约定路径
- **为什么**（用户拍板）：两种场景（MVP 从 0 创建 / 登记已有项目）都由人定义位置，系统不自作主张
- **后果**：项目元数据含本地路径字段；无 workspace 约定目录；路径合法性校验归实现层

## 002 · SOP 无管理面，全部内置写死

- **决策**：SOP 不设管理面，对用户无此概念；系统内部内置几套 SOP（编排器代码写死）。管理面只有两个：**Agent 管理面**（PI Agent 配置管理 = P002）+ **模型管理面**（系统配置模型池，Agent 从池中选 = P002 模型层）
- **为什么**（用户拍板，含推演过程）：原设想三管理面（SOP 拼 Agent / Agent 选模型 / 模型池），被硬问题击碎——**Agent 间产物传递**（上一 Agent 的产物怎么交给下一个）无法数据文件化、无法解释器化。SOP 的本质是编排器代码里显式接线的产物流，写死才是正解
- **后果**：① 内置 SOP 数量 = 编排器代码里的编排流程数量，规划 SOP 是第一个（P001）；② 「拼 Agent」的自由度收归代码层——改 SOP = 改代码，符合「厚 Agent 薄编排」与模板化哲学同源；③ P002 的「模型层」升格语义 = 模型管理面（模型池独立配置，Agent 引用）

## 003 · 架构并发、实现先串行

- **决策**：并发是任务层正式需求（同项目多任务、跨项目多任务）。数据模型、隔离、台账全按多 run 并发设计；MVP 实现一次跑一个任务，并发随后放开
- **为什么**（用户拍板）：架构不堵死并发，实现分期——隔离原料（run-id、按 run 落盘、台账）天然支持，串行起步代价小
- **后果**：P001 编排引擎按「可多实例化的单 run 引擎」写；调度器/任务队列属实现期课题，MVP 用最简串行循环
