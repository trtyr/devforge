# 各阶段 Agent 画像 · 以「阶段」为主语

> 命名规则：`change-<阶段>-<角色>`。一眼看出**这一段在干什么**，不用猜。
> 当前进度：**plan 阶段已定稿**；coding / testing 随后补。

## 阶段总览

| 阶段 | 干活的 | 审查的 | 审查对象 | 会不会碰 diff / 跑命令 |
| --- | --- | --- | --- | --- |
| plan | `change-plan-agent` | `change-plan-review` | **计划**（结合当前代码与需求） | 都不碰 |
| coding | `change-coding-agent` | `change-coding-review` | 代码改动 | 看 diff（越界二分） |
| testing | `change-test-agent` | `change-test-review` | 回归与变更测试 | 跑测试（包括新功能的验收） |

## 阶段 1 · plan

### 1.0 需求澄清

用 `ask-user-question` 问人（与 MVP 同一条 UI 链路）；问到的答案写进「需求复述」，**不猜**。

**载体口径（D024）**：歧义单独成小节（标题含「歧义」），每条写成**顶层列表行**并带分类标记——
`[必须裁决]`（需求与代码都定不下来、且影响验收口径）：必须真问用户，答复**逐字**写进同一条目的 `用户裁决：` 字段，**禁止**带默认值自决放行；
`[自决]`（不涉及验收口径）：agent 按判断定，写清理由即可。

### 1.1 这一段的产出是什么

**不是设计，是定位**：把一句需求落到「改哪几个文件的哪几行、为什么、改完怎么验」。

产出 `docs/plantree/changes/<change-id>/`：

- `change-plan.md` 六块：需求复述+模糊点 / 影响面 / 三张表（要改的·受影响不改·必须回归验证）/ 白名单 / **验收标准** / 风险
  - **不包含实施顺序**（归 coding，D015）；**不包含回归命令**（跑测试是 coding/testing 的本职，D017）
- `baseline.txt`（门 0 记录的基线 sha）
- `history.md`（往返与边界修订记录，首轮为空）

### 1.2 与 MVP `plan-agent` 的四条差别

| # | 差别 | 具体表现 |
| --- | --- | --- |
| 1 | 任务从「设计」变成「定位」 | 面对的是别人写了很久的代码：主要动作是检索与核对，不是写作 |
| 2 | 工具必须给 codegraph | `explore` 种子定位、**反向引用**（谁调用它）、正向依赖 + 配置/数据面；MVP 一个 MCP 都没有 |
| 3 | 产出从「设计文档」变成「可机械校验的合同」 | 影响面每条要 `path:line`、白名单是文件路径集合——机器能验 |
| 4 | 审查从「读文案」变成「核证据」 | MVP 审查只查通顺与矛盾；这里要查证据真不真、影响面全不全 |

### 1.3 行为约束

- **只读代码，只写 `docs/plantree/changes/<change-id>/`**
- **不得引入新依赖 / 新框架**，除非计划明写并人确认
- **不跑测试**：跑回归是 coding 的前置门与 testing 的本职；plan 不拿测试结果当证据（各段解耦）

### 1.4 输入顺序（有文档时）

1. 先读 `docs/contexts/` 建地图（README → runbook → 相关模块/实体）
2. 再用 codegraph 核实与补漏——**文档可能过期，不当真理**
3. 冲突以代码为准，并写进风险的「文档与代码不一致（`path:line`）」

### 1.5 验收条目（Q010）

需求的每一条必须写成「给什么输入 → 期望什么输出/状态」。写不出来的条目不进 coding，回人确认。

### 1.6 供给

- `change-plan-agent`：deepseek-flash，**仅 codegraph MCP**，skills 用 `plan-tree`；**并装 ask 包**（`npm:@juicesharp/rpiv-ask-user-question`，与 MVP `plan-agent` 同包）——没有它就没有能向用户发问的工具（问询环的根因行，D024）
- `change-plan-review`：grok-4.7，**仅 codegraph MCP**，thinking medium，skills 用 `plan-tree`

### 1.7 `change-plan-review` 审什么（只审计划，不看任何 diff）

| 审点 | 判据 | 谁来判 |
| --- | --- | --- |
| 证据真实 | 影响面的 `path:line` 存在、行号在范围内 | **引擎先扫**（确定性，审查官不重算） |
| 影响面完整性 | 需求涉及的入口/调用方有没有漏（这是它最有价值的判断） | 审查官（codegraph 核调用关系） |
| 边界自洽 | 「要改的」⊆ 白名单；白名单里每项都能说出改什么 | 集合关系**引擎扫**；逐项理由审查官判 |
| 验收标准可观测 | 每条是「输入→期望输出」，不是「功能正常」 | 审查官判（Q010） |
| 需求可观测 | 验收条目是「输入→期望输出」，不是「功能正常」 | 审查官判 |
| 留痕核对 | 歧义条目标了 `[必须裁决]` 的，是否带**非空**的 `用户裁决：` 字段 | **引擎先扫**（确定性：缺字段 = 硬失败，审查官不重判） |
| 分类恰当性 | 该问的（需求与代码都定不下来、且影响验收口径）有没有被标成 `[自决]` | 审查官判（语义面） |
| 风险诚实 | 看不出来的地方有没有登记，而不是跳过 | 审查官判 |

**不做什么**：不看 diff（还没有）、**不跑任何测试**、不评代码风格、不改任何文件。
**不写什么**：**新功能的测试命令**——那时测试文件还不存在，写了只能是编；它归 testing 阶段。

### 1.8 失败模式 → 对应检查

| 失败模式 | 检查手段 |
| --- | --- |
| 影响面只做 grep 级定位 | 每条影响面必须给出「谁调用它」的反向引用证据 |
| 白名单过宽（把整个 `src/` 列进去） | 白名单逐项问「这一项会被改成什么」 |
| 编造 `path:line` | 引擎扫描（复用 doc-lint 的实体检查能力） |
| 需求理解偏差 | 验收条目逐条对账 |

## 阶段 2 · coding

### 2.1 这一段干什么

照着 `change-plan.md` 改代码。第一步不是写代码，是**自己排实施步骤**：

- 产出 `impl-steps.md`（落黑板）：① ② ③，每步写「改哪些文件 / 对应哪条验收标准 / 怎么验」
- 然后按步执行、**每步一个提交**（信息含 change-id + 步骤号）
- 顺序不对、发现计划缺口 → 回 plan 补边界，而不是自己悄悄扩

为什么实施顺序不在 plan：plan agent 不是编码专家，它排的顺序没权威；顺序是实现决策，归实现者，且必须可调整。

### 2.2 与 MVP coding 的四条差别

| # | 差别 | 具体表现 |
| --- | --- | --- |
| 1 | 起点不是空白，是计划 | 输入 = 影响面 + 白名单 + 验收标准；不设计，只执行；**实施顺序由本阶段自定** |
| 2 | 动手前先证明基线是绿的 | 自己判断项目怎么跑测试（README/CI 配置/包管理器），跑一遍并存证；红就不许动 |
| 3 | 越界二分 | 白名单外 + 未申报 = FAIL；白名单外 + `<route>plan</route>` + `<impact-gap>` = 回 plan 补边界 |
| 4 | 审查从「审代码」变「对账」 | 每块 diff 都要能指回计划里的某一步；指不回去的就是无依据改动 |

### 2.3 写不写测试

**写，但只写单测，不写端到端**（沿用 MVP 口径）。

- 每个改动点至少一条单测，验证新行为或回归行为；
- **测试文件必须列在白名单里**——否则它写测试就变成越界；
- 端到端测试归 testing 阶段，coding 阶段写 e2e 一律按越界处理。

### 2.4 阶段完成条件（引擎机械判，不看自述）

1. `构建 / 类型检查 / 单测` 全绿（退出码为凭，证据落黑板）
2. `git diff --name-only <baseline>` ⊆ 白名单，或已走越界申报流程
3. 每步有提交，提交信息含 `change-id` 与步骤号
4. **文档同步**：项目有 `docs/contexts/` 时，改动涉及时必须同步更新，且 `devforge doc-lint` 退出码为 0（与 MVP coding 同款门）

### 2.4b 标记与重推（有界）

- 每步完成 → `<stage-complete>N</stage-complete>`（N = 步骤号）
- 无标记 → 重推上限 **3 次**；第 4 次判基础设施故障（MVP 零上限，change 不照抄）
- 想越界 → `<route>plan</route>` + `<impact-gap>`，不打标记

### 2.5 `change-coding-review` 审什么

| 审点 | 判据 |
| --- | --- |
| 对账 | 每块 diff 能指回 `impl-steps.md` 的某一步 + 计划的影响面/边界；指不回去 = 无依据改动 = FAIL |
| 越界 | 引擎给出 diff 与白名单的比对；有越界无申报 = FAIL |
| 依赖 | 新增依赖（`requirements` / `package.json` / `Cargo.toml` 的 diff）未在计划里写 = FAIL |
| 可构建 | 自己跑构建 + 与改动直接相关的目标测试（分钟级），全量回归留给 testing |
| 一致性 | 跟项目既有写法走（命名/分层/错误处理），不夹带风格重写 |
| 测试真实性 | 新增单测不是空断言、不是只走 happy path、能反向变红 |

**不做什么**：不重写代码、不改文件、不跑全量回归（那是 testing 的事）。

### 2.6 供给

- `change-coding-agent`：deepseek-flash + **codegraph + context7** + 四语言 best-practices 技能（与 MVP `coding-agent` 同款供给，仅提示词换成 change 纪律）
  - **为什么给 context7**：它跟 MVP coding 一样在真写代码，改的又常常是别人库的调用；不给文档等于蒙眼改，只能靠猜 API 形状
- `change-coding-review`：grok-4.7 + codegraph（不需要 context7——审查不靠写实现，靠对账与读 diff），thinking medium，能跑命令（只读验证）

> 供给锚点已在单测里钉住（T008b），后续改供给必须先改这一节。

## 阶段 3 · testing

### 3.1 这一段干什么

证两件事：**改的东西生效了** + **别的东西没坏**。

MVP 只证第一件；change 必须两件都证，而且顺序是先证第二件。

### 3.2 与 MVP testing 的差别

| # | 差别 | 具体表现 |
| --- | --- | --- |
| 1 | 起点是既有系统 | 有现成测试套件 → **先跑全套回归**，红就停 |
| 2 | e2e 只补变更点 | 不为新需求重建整套测试，避免 diff 撑大、避免测旧功能出假问题 |
| 3 | 验收要逐条对账 | plan 的每条验收标准都要指到一个测试的 `path:line`，缺一条 = FAIL |
| 4 | 回归失败直接丢回 coding | 测试 Agent 不看代码、不做定位；它只负责证伪，定位是实现方的事 |

### 3.3 流程（五步）
1. **回归**：agent 自己判断怎么跑（README / CI / 包管理器），跑全套既有测试，输出落 `evidence/regression.log`（命令 + 退出码 + 尾巴）。**红 → 直接 `<route>coding</route>`**。
2. **补变更 e2e**：只针对变更点，从用户可见入口走（有 Runbook 就照它起系统；库形态则调公开 API）。
3. **验收对账**：输出 `验收对照表`（每条验收标准 → 测试 `path:line`）；引擎核 `path:line` 存在性，缺一条 = FAIL。
4. **反向验证**：至少一条测试能变红（把实现改坏它必须失败），防假绿。
5. **可靠性纪律**（C22）：自指跑全套一票否决、每个外部命令带超时、进程组回收与临时目录、无共享状态/顺序依赖、报时长、禁交互或无限等待。

### 3.4 两条硬约束

- **不许改产品代码**：发现 bug → `<route>coding</route>`；发现需求理解错了 → `<route>plan</route>`。测试和实现不能是一家人。
- **不给 codegraph**（沿 MVP 黑盒纪律）：给了就会写出贴着内部实现的测试，改一次就碎。

### 3.5 `change-test-review` 审什么

| 审点 | 判据 |
| --- | --- |
| 回归真跑 | `evidence/regression.log` 有命令与退出码；声称绿但无证据 = FAIL |
| 验收对账 | 每条验收标准都有测试对应；空断言、只跑 happy path = FAIL |
| 反向验证 | 至少一条能证伪；拿不出证据 = FAIL |
| 测试自身可靠 | C22 七条逐条对；自指跑全套 = 一票否决 |
| 未改产品代码 | diff 里不准出现非测试文件；出现即 FAIL |
| e2e 范围 | 只针对变更点；顺手重建全套 = 无依据改动 |

### 3.6 引擎侧机械检查（不看自述）

- `验收对照表` 里的 `path:line` 是否存在（复用实体检查）
- diff 是否只含测试文件与计划白名单内的文件
- `evidence/regression.log` 是否有非零退出码而仍声称通过（直接 FAIL）

### 3.7 供给

- `change-test-agent` / `change-test-review`：与 MVP `test-agent` / `test-review` 同款（**不给 codegraph**），提示词换成 change 纪律。

### 3.8 标记与回退

- 每阶段完成 → `<stage-complete>N</stage-complete>`；无标记重推上限 3 次
- 测试 review FAIL → `<route>coding</route>`（默认）或 `<route>plan</route>`（需求理解错）
- 回归红 → `<route>coding</route>`，不定位、不分析原因

### 3.9 检查点

`docs/plantree/changes/<id>/state.json`，**引擎写、agent 不碰**：

```json
{
  "phase": "coding|testing|done",
  "baseline_sha": "…",
  "roundtrips": 1,
  "impl_steps_done": [1, 2],
  "acceptance_done": ["#1", "#3"],
  "review_rounds": 4,
  "updated_at": "…"
}
```

续跑从断点继续；`roundtrips` 跨会话保留（上限 3）。

## 阶段 4 · 收尾（无 Agent）

不跑任何 agent。引擎写 `docs/plantree/changes/<id>/report.md`：墙钟、diff 统计（文件数/增删行）、审查轮次、往返次数、用量（从会话账汇总）、验收对账结果。
文档本身已由 coding agent 在改动时写好（`doc-contract` + `doc-lint` 门），不再单独一趟。
