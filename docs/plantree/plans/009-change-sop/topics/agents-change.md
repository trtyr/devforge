# 各阶段 Agent 画像 · 以「阶段」为主语

> 命名规则：`change-<阶段>-<角色>`。一眼看出**这一段在干什么**，不用猜。
> 当前进度：**plan 阶段已定稿**；coding / testing 随后补。

## 阶段总览

| 阶段 | 干活的 | 审查的 | 审查对象 | 会不会碰 diff / 跑命令 |
| --- | --- | --- | --- | --- |
| plan | `change-plan-agent` | `change-plan-review` | **计划**（结合当前代码与需求） | 都不碰 |
| coding | `change-coding-agent` | `change-coding-review` | 代码改动 | 看 diff（越界二分） |
| testing | `change-test-agent` | `change-test-review` | 回归与变更测试 | 跑测试（包括新功能的验收） |

## 阶段 1 · plan

### 1.1 这一段的产出是什么

**不是设计，是定位**：把一句需求落到「改哪几个文件的哪几行、为什么、改完怎么验」。

产出 `docs/plantree/changes/<change-id>/`：

- `change-plan.md` 七块：需求复述+模糊点 / 影响面 / 三张表（要改的·受影响不改·必须回归验证）/ 白名单 / **验收标准 + 回归命令** / 风险 / **实施顺序**
- `baseline.txt`（门 0 记录的基线 sha）
- `evidence/baseline-test.log`（**基线**测试的运行证据：命令、退出码、输出尾巴）
- `history.md`（往返与边界修订记录，首轮为空）

### 1.2 与 MVP `plan-agent` 的四条差别

| # | 差别 | 具体表现 |
| --- | --- | --- |
| 1 | 任务从「设计」变成「定位」 | 面对的是别人写了很久的代码：主要动作是检索与核对，不是写作 |
| 2 | 工具必须给 codegraph | `explore` 种子定位、**反向引用**（谁调用它）、正向依赖 + 配置/数据面；MVP 一个 MCP 都没有 |
| 3 | 产出从「设计文档」变成「可机械校验的合同」 | 影响面每条要 `path:line`、白名单是文件路径集合——机器能验 |
| 4 | 审查从「读文案」变成「核证据」 | MVP 审查只查通顺与矛盾；这里要查证据真不真、影响面全不全 |

### 1.3 行为约束

- **只读代码，只写 `docs/plantree/changes/<change-id>/`**
- **不得引入新依赖 / 新框架**，除非计划明写并人确认
- 允许跑**只读验证命令**（跑既有测试看基线、复现 bug），用于 `evidence/baseline-test.log`；禁止改源码、`git commit`、安装依赖

### 1.4 输入顺序（有文档时）

1. 先读 `docs/contexts/` 建地图（README → runbook → 相关模块/实体）
2. 再用 codegraph 核实与补漏——**文档可能过期，不当真理**
3. 冲突以代码为准，并写进风险的「文档与代码不一致（`path:line`）」

### 1.5 验收条目（Q010）

需求的每一条必须写成「给什么输入 → 期望什么输出/状态」。写不出来的条目不进 coding，回人确认。

### 1.6 供给

- `change-plan-agent`：deepseek-flash，**仅 codegraph MCP**，skills 用 `plan-tree`
- `change-plan-review`：grok-4.7，**仅 codegraph MCP**，thinking medium，skills 用 `plan-tree`

### 1.7 `change-plan-review` 审什么（只审计划，不看任何 diff）

| 审点 | 判据 | 谁来判 |
| --- | --- | --- |
| 证据真实 | 影响面的 `path:line` 存在、行号在范围内 | **引擎先扫**（确定性，审查官不重算） |
| 影响面完整性 | 需求涉及的入口/调用方有没有漏（这是它最有价值的判断） | 审查官（codegraph 核调用关系） |
| 边界自洽 | 「要改的」⊆ 白名单；白名单里每项都能说出改什么 | 集合关系**引擎扫**；逐项理由审查官判 |
| 实施顺序可用 | 步骤有先后依赖、每步能落到文件与验收标准；不是把白名单照拄一遍 | 审查官判 |
| 回归命令可执行 | 命令具体、有工作目录、有通过标准、有超时；不是「跑一下全部测试」 | 审查官读（**不执行**） |
| 验收标准可观测 | 每条是「输入→期望输出」，不是「功能正常」 | 审查官判（Q010） |
| 基线证据一致 | `evidence/baseline-test.log` 的命令与计划一致；失败已进风险 | 审查官核 |
| 需求可观测 | 验收条目是「输入→期望输出」，不是「功能正常」 | 审查官判 |
| 风险诚实 | 看不出来的地方有没有登记，而不是跳过 | 审查官判 |

**不做什么**：不看 diff（还没有）、不跑命令（基线由 agent 自己跑并落证据）、不评代码风格、不改任何文件。
**不写什么**：**新功能的测试命令**——那时测试文件还不存在，写了只能是编；它归 testing 阶段。

### 1.8 失败模式 → 对应检查

| 失败模式 | 检查手段 |
| --- | --- |
| 影响面只做 grep 级定位 | 每条影响面必须给出「谁调用它」的反向引用证据 |
| 白名单过宽（把整个 `src/` 列进去） | 白名单逐项问「这一项会被改成什么」 |
| 编造 `path:line` | 引擎扫描（复用 doc-lint 的实体检查能力） |
| 回归命令糊成「跑一下全部测试」 | 审查官读：要具体命令 + 通过标准 + 超时 |
| 需求理解偏差 | 验收条目逐条对账 |

## 阶段 2 · coding

### 2.1 这一段干什么

照着 `change-plan.md` 改代码：按「实施顺序」逐步推，每步一个提交，改完自证（构建/单测/既有测试）。

### 2.2 与 MVP coding 的四条差别

| # | 差别 | 具体表现 |
| --- | --- | --- |
| 1 | 起点不是空白，是计划 | 输入 = 影响面 + 白名单 + 实施顺序 + 验收标准；不设计，只执行 |
| 2 | 动手前先证明基线是绿的 | 跑一遍回归命令，红就不许动（否则改完分不清是谁弄坏的） |
| 3 | 越界二分 | 白名单外 + 未申报 = FAIL；白名单外 + `<route>plan</route>` + `<impact-gap>` = 回 plan 补边界 |
| 4 | 审查从「审代码」变「对账」 | 每块 diff 都要能指回计划里的某一步；指不回去的就是无依据改动 |

### 2.3 写不写测试

**写，但只写单测，不写端到端**（沿用 MVP 口径）。

- 每个改动点至少一条单测，验证新行为或回归行为；
- **测试文件必须列在白名单里**——否则它写测试就变成越界；
- 端到端测试归 testing 阶段，coding 阶段写 e2e 一律按越界处理。

### 2.4 阶段完成条件（引擎机械判，不看自述）

1. `构建 / 类型检查 / 单测` 全绿（退出码为凭，证据落黑板）
2. `git diff --name-only <baseline>` ⊆ 白名单，或已走越界申报流程
3. 每步有提交，提交信息含 `change-id` 与步骤号

### 2.5 `change-coding-review` 审什么

| 审点 | 判据 |
| --- | --- |
| 对账 | 每块 diff 能指回计划里的第几步；指不回去 = 无依据改动 = FAIL |
| 越界 | 引擎给出 diff 与白名单的比对；有越界无申报 = FAIL |
| 依赖 | 新增依赖（`requirements` / `package.json` / `Cargo.toml` 的 diff）未在计划里写 = FAIL |
| 可构建 | 自己跑构建 + 与改动直接相关的目标测试（分钟级），全量回归留给 testing |
| 一致性 | 跟项目既有写法走（命名/分层/错误处理），不夹带风格重写 |
| 测试真实性 | 新增单测不是空断言、不是只走 happy path、能反向变红 |

**不做什么**：不重写代码、不改文件、不跑全量回归（那是 testing 的事）。

### 2.6 供给

- `change-coding-agent`：deepseek-flash + codegraph + context7 + 四语言 best-practices 技能（与 MVP `coding-agent` 同款，但提示词换成 change 纪律）
- `change-coding-review`：grok-4.7 + codegraph，thinking medium，能跑命令（只读验证）
