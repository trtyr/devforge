# 各阶段 Agent 画像（worker / reviewer）· 与 MVP 的差别

> 一次只写一段，写完再过下一段。当前：**plan 阶段**。

## 阶段 1 · plan

### 1.1 MVP 的 plan-agent 是什么样（真源：`manifest.rs` builtin）

- 供给：deepseek-flash / **无任何 MCP** / skills 只有 `plan-tree`
- 提示词只有五条职责：读 skill → 问用户 → 产出 plan tree → 确认后打完成标记 → 小步快跑
- 面对的是空白仓，所以它的核心动作是**想清楚要做什么**（设计、拆任务、定验收）

### 1.2 change 的 plan-agent 差在哪（四条）

| # | 差别 | 具体表现 |
| --- | --- | --- |
| 1 | 任务从「设计」变成「定位」 | 不再产出功能方案，而是把需求落到**既有代码的文件与符号**上；主要动作是检索与核对，不是写作 |
| 2 | 工具必须给 codegraph | 三件事 MVP 一件都不需要：`explore` 种子定位、**反向引用**（谁调用它）、正向依赖 + 配置/数据面（改默认值、改表结构会炸在哪） |
| 3 | 产出从「设计文档」变成「可机械校验的合同」 | 六块里两块机器可验：影响面每条的 `path:line` 是否真实存在；白名单是否是文件路径集合 |
| 4 | 审查职责相反 | MVP 审查怕管太宽只读文案；change 审查要**核账**（证据真实性、边界自洽、验收命令亲自跑） |

### 1.3 行为约束（MVP 不需要的两条）

- **只读代码，只写 `docs/plantree/changes/<change-id>/`**：其余文件一律不写。
- **不得引入新依赖 / 新框架**，除非计划里明写并经过人确认——否则“顺手换个库”就是另一种范围膨胀。

### 1.4 供给（2026-10-20 定）

- profile `change-plan`：deepseek-flash，**仅 codegraph MCP**（不给 context7——改既有代码主要靠结构信息）
- skills：`plan-tree`（计划结构）+ 复用 `doc-contract`？**不给**——它写的不是实体文档，是计划；契约在这里会制造无意义的必填节
- 允许跑**只读验证命令**：跑一次既有测试看基线是否绿、复现 bug。禁止改源码、禁止 `git commit`、禁止安装依赖；命令产生的缓存/构建物必须登记进风险表

### 1.5 输入顺序（有文档时）

1. 先读 `docs/contexts/`（README → runbook → 相关模块/实体）建立地图
2. 再用 codegraph 核实与补漏——**文档可能过期，不当真理**
3. 冲突时以代码为准，并在计划的「风险」里记一条「文档与代码不一致（`path:line`）」

### 1.6 产出

`docs/plantree/changes/<change-id>/` 下：

- `change-plan.md`：六块（需求复述+模糊点 / 影响面 / 三张表 / 白名单 / 验收命令 / 风险）
- `baseline.txt`：门 0 记录的基线 sha
- `history.md`：往返与边界修订记录（首轮为空）

**验收条目（Q010）**：需求的每一条必须写成「给什么输入 → 期望什么输出/状态」；写不出来的条目不进 coding，回到人。

### 1.7 失败模式 → 对应检查

| 失败模式 | 检查手段 |
| --- | --- |
| 影响面只做了 grep 级定位 | 审查要求每条影响面给出「谁调用它」的反向引用证据 |
| 白名单过宽（把整个 `src/` 列进去） | 审查对白名单逐项问「这一项会被改成什么」 |
| 编造 `path:line` | `doc-lint --repo` 的实体存在性检查（已有能力） |
| 验收命令糊成「跑一下全部测试」 | 审查官亲自执行，并要求给出具体命令与通过标准 |
| 需求理解偏差 | 验收条目（输入→期望输出）逐条对账 |
