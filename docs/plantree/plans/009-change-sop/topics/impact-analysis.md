# 影响面分析 · 口径与 codegraph 用法

> 本文件只回答一件事：**怎么从一个需求，走到“要改哪几个文件的哪几行”**，且证据可核。

## 为什么不能靠读代码猜

一个需求落到代码上，答案有三层：

1. **直接命中**：需求里的名词/动词对应的符号（`login`、`timeout`、`create_note`）
2. **调用链**：谁调它、它调谁（改签名会波及上层，改语义会影响下层）
3. **隐式耦合**：配置键、数据表、错误码、序列化格式——名字不在需求里，但改了就炸

第 3 层靠 grep 几乎必漏，靠 codegraph 的引用/被引用查询才不会。

## codegraph 查询序列（每步都要留 path:line）

1. `explore`：以需求关键词为种子，拿到候选文件与符号
2. **反向查**：目标符号被谁引用（决定“受影响但不改”的名单）
3. **正向查**：目标符号依赖什么（决定“必须回归验证”的范围）
4. 配置/数据面：`doc-inventory` 的 `config` / `data` 条目里找同域入口（改了配置默认值、改了表结构，都藏在这里）

## 三张表的判定口径

| 表 | 判定 | 反例（会导致 FAIL） |
| --- | --- | --- |
| 要改的 | 必须修改才能满足需求；每条给出「改什么/为什么」 | 把“可能相关”的都塞进来 |
| 受影响但不改 | 被本次改动的语义波及，但接口与行为保持兼容 | 漏掉调用方（改完编译不过就是这里漏的） |
| 必须回归验证 | 有既有测试覆盖、或行为可观测的点 | 一句“跑一下全部测试”糊过去 |

## 白名单的写法

- 文件级路径，相对仓库根：`src/auth/session.py`
- 允许新增：`src/auth/token.py (新增)`
- 明确不碰的写进「边界外」段落（例：`src/legacy/*`、`migrations/`）

## 验收命令的要求

- 必须是**能直接跑**的命令（`pytest tests/auth -q`），不是描述（“跑一下认证测试”）
- 审查官**亲自跑一遍**；跑不过就是 FAIL，不接受“应该能过”
- 没有测试套件时，命令写「先写行为快照再跑」，并把这条登记进风险表（Q006）
