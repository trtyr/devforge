# 边界协议 · 越界二分与 plan⇄coding 往返

> 本文件定义 change SOP 与 MVP 最本质的差别：**它不是单向流水线，是带回路的状态机**。
> 核心问题：coding 阶段动到了计划边界之外的文件，怎么判？

## 一、为什么不能只看 diff

两种越界在 `git diff --name-only` 里长得一模一样：

| 情形 | 本质 | 该怎么处理 |
| --- | --- | --- |
| A. 范围膨胀 | 计划边界正确，coder 顺手多改（重构、格式化、改无关文件） | **硬 FAIL**，一票否决 |
| B. 计划缺口 | 计划漏了必需文件，coder 干到一半发现不改就做不成 | **打回 plan 补边界**，不是罚 coder |

用 diff 直接判 FAIL，等于把 B 逼成两种坏结果：coder 撒谎说“改完了”（实际用了绕路的错方案），
或者偷偷改完不申报。两种都比返工贵。

## 二、判据：有没有先回 plan

```
coding 完成 → 引擎算 diff --name-only <baseline>
├─ ⊆ 白名单                          → 进 testing
├─ 越界 + agent 输出 <route>plan</route> + <impact-gap> 清单
│                                   → 打回 plan（只许改影响面/三张表/白名单）
│                                   → 边界增量过 change-review
│                                   → 带新边界重进 coding
└─ 越界 + 无 route/impact-gap        → FAIL：范围膨胀
```

`<impact-gap>` 每条必须含：**文件路径 / 为什么非改不可 / 证据**（`path:line` 或调用链）。
没有证据的“我觉得要改”按范围膨胀处理。

## 三、边界修订的审查（防边界蠕变）

只允许 plan 阶段改：「影响面（第 2 块）」「三张表（第 3 块）」「白名单（第 4 块）」原文，
其余四块（需求复述/验收命令/风险）只能追加不能重写。

change-review 对边界增量只审三件事：
1. 新加的文件是否真的被需求波及（要证据，不接受“顺手”）
2. 原白名单里**没有**被删项（删白名单 = 缩小范围，必须写原因）
3. 新边界下的验收命令是否仍然可执行

## 四、往返的上限

- 同一 change 的「plan→coding 往返」最多 3 次；第 4 次说明需求本身没想清楚 → 停下问人。
- 每次往返都在 `docs/plantree/changes/<change-id>/history.md` 记一条：时间、新增文件、理由、审查结论。
- 往返不改基线 sha（否则 diff 失去意义）；基线只在门 0 建立一次。

## 五、与 MVP 的编排差异（为什么必须单开 SOP）

| 面 | MVP（单向） | change（带回路） |
| --- | --- | --- |
| 阶段图 | plan → coding → testing | plan ⇄ coding ⇄ testing，带路由 |
| 失败语义 | 打回当前阶段重做 | 可能**跨阶段回退**（coding 发现计划缺口 → 回 plan） |
| 证据锚 | 阶段产物 | 阶段产物 + **基线 diff** |
| 结束条件 | 测试通过 | diff ⊆ 边界 + 回归绿 + 文档同步 + 报告 |
| 关键机械检查 | 阶段标记 / 审查协议 | 上述 + 白名单比对 + 回归命令退出码 |

结论：复用三个**阶段**的提示词与审查纪律，但编排器另写一个（状态机 + 基线 + 往返计数）。
