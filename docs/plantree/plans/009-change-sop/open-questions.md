# change · 待定问题

编号规则：`Q0NN`。关闭时在下面写「结论」并同步到 `decisions/README.md`。

## Q001 需求以什么形态进来？
自然语言一句话 / 结构化（目标-约束-验收）/ issue 链接？
**暂定**：先支持一句话 + 可选验收要点；其它形态由调用方转写后传入。

## Q002 白名单粒度
文件级？目录级？还是「文件级 + 允许新增文件但必须在指定目录」？
**暂定**：文件级；新增文件允许，但必须显式列在「要改的」表里（新增 = 白名单里的新路径）。

## Q003 大仓 `git init` 的风险
`.git` 缺失但仓库很大 / 含大二进制时怎么办？
**结论（2026-10-20 关闭）**：不设体积守卫——**全部登记、全部提交**。理由：这种大仓大概率本来就有 git（也就走不到 init 分支）；而一旦没有，漏提交的文件正是后面 diff 看不到的盲区。→ D008

## Q004 change-id 规则
`change-20261020-fix-login-timeout`？
**暂定**：`change-<yyyymmdd>-<slug>`；同一任务重复触发沿用已存在的 id。

## Q005 文档收尾用哪条链
`docs-update`（本地增量）还是 `docs-sync`（远端对齐）？还是两条都跑？
**暂定**：默认 `docs-update`；远端是否同步由调用方决定（engram 是镜像，不是真源）。

## Q006 项目没有测试套件怎么办
回归无从谈起。
**暂定**：plan 阶段必须识别「无测试套件」，并在风险表里登记；此时 testing 阶段要求先写**行为快照测试**（对变更点做输入输出快照），再改代码。

## Q007 与 MVP 的 plan-tree 编号空间
`docs/plantree/plans/` 下 MVP 计划用 001-009 连续编号，变更计划是否也进这个空间？
**结论（2026-10-20 关闭）**：不进。变更计划落 `docs/plantree/changes/<change-id>/`，与产品级计划分开。

## Q008 越界维修回 plan 后，要不要重跑整个 plan？
**暂定**：不重跑。只允许改六块里的影响面/三张表/白名单，且增量过 change-review；详见 `topics/boundary-protocol.md`。

## Q009 往返次数上限
**暂定**：3 次。第 4 次说明需求本身没想清楚 → 停下问人。

## Q010 “做对了没有”由谁判
MVP 有完整需求文档可对照；change 往往只有一句话，验收标准容易变成“跑得过就算对”。
**暂定**：plan 阶段必须把需求拆成**可观测的验收条目**（给输入 → 期望输出/状态变化），testing 阶段逐条对账；
验收条目写不出来的需求，plan 阶段就应停下来问人（不允许带着“大概吧”进入 coding）。
