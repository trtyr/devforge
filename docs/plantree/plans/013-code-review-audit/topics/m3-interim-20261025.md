## 四、暴露的两个设计缺陷

0. **【铁律违反，用户 10-25 严厉拍板】最终产物禁止落在临时目录**——说了五六遍的规矩，
   本次 M3 又踩：验收环境架在 /var/tmp（重启即清）+ findings 只在进程内存 + 会话文件被
   轮转清理，三处叠加 = 61 批一夜成果不可恢复，**等价白干**。
   **程序化守卫（处置方案候选，待用户拍板后才动工）**：devforge serve 启动时校验 --root /
   plans_root / workspace，命中 /tmp、/var/tmp 及一切 tmpfs 挂载点直接拒绝启动（fail fast，
   带报错信息指向持久路径）；审计 runner 每批 findings 即时落黑板（缺陷①同步修）。
   **行为铁律（对 AI 与人同样生效）**：任何跑完才能拿到的产物（报告/测试结果/审计发现）
   必须在产出的当下就写入项目目录或专用持久目录；tmp 只允许放「丢了也无所谓」的中间垃圾。

1. **批次 findings 不落黑板（新发现，M1 断点设计缺口）**：Progress 只记 done_batches id，
   发现本体在 runner 内存 Vec——c 进程被杀，**61 批的全部发现丢失且不可恢复**（对应会话
   jsonl 已被会话目录轮转清理）。续跑产出的报告将只含 62-87 批 + Stage 2，缺前 61 批。
   方向：每批 findings 落黑板（audit-findings/{unit}.json），Progress 记 id 报告组装时回读。
   **处置决策待拍板（10-25 提出）：① 先修 findings 落黑板再全量重跑（~4h 换完整 87 批报告）；
   ② 不修继续跑，报告以 62-87 + Stage 2 过 M3 质量底线（完整性打折）；修复本身无论选哪边
   都要落地，只是重跑与否的差别。**
2. **store 纯内存**（已记 backlog 第四节，用户拍板）：重启即蒸发，本次事故中 budget
   尸检无法进行即由此导致。

## 五、事故处置与经验

- 断点续跑机制（M1 Progress）实战可用：61 批进度跨进程存活，续跑零重复劳动。
- 看门狗带 STALLED 检测重挂（>15 分钟无进度报警），5h 窗口。
- **教训**：长跑流水线的每个阶段产物必须即时落黑板，内存态只允许作为缓存——
  「先落盘再打勾」，否则断点续跑只是重跑调度器而非真正的断点。
