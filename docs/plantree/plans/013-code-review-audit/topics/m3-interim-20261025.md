## 一、Stage 0 规划产出（audit-stage0.json，质量良好）

对 87 个批次做元数据规划：**priority 37 批 / skip 19 批 / 跨单元假设 4 条**。

跨单元假设（Stage 2 将逐一验证）：

1. **错误处理一致性**：change/*、sop/doc/*、engine/* 三条链路是否共用同一错误分类与
   上下文链（src/error.rs 为唯一 Taxonomy 入口，还是各层自造 enum）；基础设施故障是否
   被误当作质量失败上报。
2. **可观测性可重建性**：events.rs 定义的事件名/schema 是否被 change、sop、server 一致
   复用；是否存在 println/tracing 绕过事件通道的旁路，导致无法从日志重建一次 run 的动作序列。
3. **状态迁移与持久化一致性**：change/state.rs、change/session.rs、runstate/{mod,resume}.rs、
   domain/store.rs 对同一 run 状态的迁移集合、落盘格式、恢复点是否一一对应（resume 是否
   覆盖所有可中断点）。——**事后注：这条假设已经意外命中真实缺陷**（store 纯内存 +
   findings 不落黑板，见第四节），审计假设的杀伤力先于报告得到验证。
4. **三套 SOP 协议能力对齐**（doc/coding/testing 协议族横向比对）。

## 四、暴露的两个设计缺陷

1. **批次 findings 不落黑板（新发现，M1 断点设计缺口）**：Progress 只记 done_batches id，
   发现本体在 runner 内存 Vec——c 进程被杀，**61 批的全部发现丢失且不可恢复**（对应会话
   jsonl 已被会话目录轮转清理）。续跑产出的报告将只含 62-87 批 + Stage 2，缺前 61 批。
   方向：每批 findings 落黑板（audit-findings/{unit}.json），Progress 记 id 报告组装时回读。
2. **store 纯内存**（已记 backlog 第四节，用户拍板）：重启即蒸发，本次事故中 budget
   尸检无法进行即由此导致。

## 五、事故处置与经验

- 断点续跑机制（M1 Progress）实战可用：61 批进度跨进程存活，续跑零重复劳动。
- 看门狗带 STALLED 检测重挂（>15 分钟无进度报警），5h 窗口。
- **教训**：长跑流水线的每个阶段产物必须即时落黑板，内存态只允许作为缓存——
  「先落盘再打勾」，否则断点续跑只是重跑调度器而非真正的断点。
