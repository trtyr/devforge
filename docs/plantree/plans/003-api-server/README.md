# P003 · API 接口体系与服务器形态

## Scope

**devforge 的产品形态是服务器，不是 CLI**（用户拍板 2026-10-16）。本项目定义并落地一整套健全的 API 接口体系，作为所有能力的唯一出口——未来前端对接、任何客户端消费，都走这一套接口。

**为什么是服务器：**
- 未来有前端：流程图可视化（原则 §4 的宿主）、节点下钻、session trace 展示，全部由前端通过 API 消费
- 交互中继重构：Plan Agent 的对话流、ask-user-question 的 UI 子协议，不再渲染到终端，而是经 API 推给客户端、答案经 API 回传
- 编排控制面：创建项目/任务、启动流程、查状态——都是服务接口，不是命令行参数

## API 能力域（从现有设计导出，清单待 T002 细化）

| 能力域 | 内容 | 来源 |
|--------|------|------|
| 编排控制 | 项目/任务管理、启动规划流程、查运行图状态 | P001 状态机 |
| 交互中继 | Agent 对话流式转发、ask-user-question UI 事件推送与答案回传 | P001 decisions/008 + T006 extension UI 子协议 |
| 可观测 | DAG 运行图、节点下钻（日志/think/事件流）、session trace | 原则 §4 + P001 T011 |
| 配置管理 | 模板编辑、每 Agent 模型选择（P002 的两个开放面） | P002 decisions/002/003 |

## 与 P001/P002 的关系

- P001 编排器内核跑在服务器进程内；其「用户交互中继」职责的实现面从终端改为 API（MVP 期可用裸 HTTP 客户端调试）
- P002 的管理面（模板 + 模型选择）经 API 暴露
- P001 T006 骨架按服务器形态写（不再按 CLI）
