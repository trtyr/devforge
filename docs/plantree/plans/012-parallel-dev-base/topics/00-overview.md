# 00 · 底座总览：原则、判据、失败模式

> 来源：2026-10-24 业界研究综合（Compound Engineering 设计模式 / OpenAI harness engineering /
> Anthropic context engineering / intentic / orcyx / Augment 等 worktree 编排实践）。

## 核心命题

并行开发不是「多开几个 agent」，是「**调度 + 合并**」问题。加速上限由串行分数决定
（Amdahl：规格/契约/集成/评审占 40% 时，无限 worker 上限 2.5x），实际还受下游容量
（组合验证、merge queue、评审）约束。**优化目标 = 最短的「已接受需求 → 已验证集成行为」安全路径，
不是 worker 数量。**

## 五特征判据（每个设计决策的裁判）

| 特征 | 问题 |
| --- | --- |
| 局部性 | 完成该任务需要触碰几处？ |
| 爆炸半径 | 改动外溢的范围有多大？ |
| 边界完整性 | 从局部证据能否推断正确契约？ |
| 可导航性 | 陌生 agent 多快找到正确入口（渐进披露）？ |
| 窄验证回路 | 改动能否窄验证（agent 自纠的前提）？ |

## 工作项契约（分解的是变更图，不是待办清单）

有用的工作项 = 清晰输入 revision + 有界所有权 + 显式产出 + 验收声明 + **对他人未提交状态零隐藏依赖**。
派发前六问（任一否 = 保持串行直到边界建立）：

1. 每个 worker 能对着不可变输入独立完成吗？
2. 共享契约已版本化，或有显式契约 owner 吗？
3. 产出能在集成前独立验证吗？
4. 某 worker 失败/取消会使无关工作作废吗？
5. 集成有确定性顺序吗？
6. 组合验证成本在下游容量内吗？

## 冲突五级（文本 merge 成功 ≠ 安全）

1. 文本冲突（同行 overlap）→ merge 工具可见
2. 结构冲突（文件合了但 import/生成物/schema 版本不一致）
3. **语义冲突**（各自编译通过、合在一起违反不变量）——文本工具全盲
4. 操作冲突（rollout 顺序/容量不兼容）
5. 权威冲突（对同一受保护契约做出不同决策）

预防 = 契约/schema/迁移/生成物单一 owner；消费者用 owner 的 fixture 或 pin 的预发布产物，
不自带本地变体。

## 隔离三原则

1. **worktree ≠ 沙箱**：隔离了文件不隔离权限——change agent 有 bash，能摸宿主凭证与网络。
   执行隔离必须容器化（M2）。
2. **pin base**：worker 实现期不得追逐移动目标（毁灭可复现性）；目标移动由集成阶段处理。
3. **清理是工作流**：孤儿 worktree/进程/secrets 的清理所有权在 worker 崩溃时转移给平台。

## 失败模式表（节选自业界，每条都要有响应）

| 失败 | 后果 | 响应 |
| --- | --- | --- |
| 两 worker 拥有同一 schema | 客户端与迁移分叉 | 契约单一 owner + 版本化发布 |
| worker 共享目录 | 改动丢失/不可归因 | 每 work item 唯一 worktree/index/branch |
| worktree 当沙箱用 | 仓代码摸到宿主凭证 | 容器/microVM + 能力收敛（M2） |
| 候选测试过在过期 base 上 | 目标移动后假信心 | 集成阶段 reapply + 受影响验证重跑 |
| 文本 merge 成功、不变量崩 | 语义冲突 | 组合契约/属性/集成检查 |
| merge queue 饱和 | 分支老化反复重试 | 准入控制 + queue-age 策略 |
| worker 死时持有保留权 | 共享契约被堵 | 租约 + 集成权威 fencing |
| 取消留下进程 | 资源/凭证泄漏 | 进程组拆除 + 被追踪的清理 |

## 与 devforge 现状的映射

**已有（复用）**：runstate 断点、事件流 + SSE、断路器、失活收割、doc-lint/coverage/测试
（组合验证工具箱）、plantree 依赖聚类（首批 DAG 输入）。
**缺失（本计划补）**：work-item 契约、worktree 生命周期、所有权模型、merge queue + CAS、
准入控制、沙箱 spawn。
