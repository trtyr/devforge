# Open Questions — P012 并行开发底座

> 待用户拍板。每条附操作员倾向。

## Q1 · 沙箱起点选型

~~Plain Docker vs 直接上凭证代理形态~~ **已评估定论（2026-10-24）：主体 = pi 原生 Plain Docker，
srt (Anthropic sandbox-runtime) 仅作二期可选的网络白名单嵌套层，不引外部插件当主体。**
评估详见 topics/05 选型评估节（核心：srt 只包 bash 进程树漏内置工具、Gondolin 自认不是凭证边界、
Docker 一层罩文件/凭证/资源三面且 spawn 协议零改动）。

## Q2 · 集成节奏

候选通过组合验证后：立即集成进 master（每候选即合，merge queue 模式），还是攒批
（如每日一批次序集成）？
**倾向**：立即即合——devforge 自举场景候选少而频率低，攒批只会增加 base 漂移。

## Q3 · 首份所有权表草案确认

03 里的 devforge 自举所有权表（src/config 归批 A、src/server/mod.rs 归 ARC-R2 独占……）
是否照此初始化？
**倾向**：照此初始化，跑一轮后按实际冲突修订。

## Q4 · 串行分数的「spec 段」口径

规格收敛含用户拍板等待时间吗？含的话串行分数会很高（用户睡觉=全局串行），
但这是诚实数字；不含的话加速比会虚高。
**倾向**：分两口径报告——「含人等待」与「纯机器关键路径」，决策用后者，预期管理用前者。

## Q5 · 第一批并行试点选谁

批 D（DR-17/18，独立小件）先进 worktree 验证全链路，还是直接批 A + 批 D 双开？
**倾向**：先批 D 单线过一遍 M0-M3 全链路（契约→worktree→沙箱→集成），通了再双开。
理由：批 A 是最重的语义改动，不适合当新底座的小白鼠。

## Q6 · AF/ARC 派工与底座建设的先后

底座（本计划）先行，还是先派工一两个 AF 小件（用现状 change SOP，无隔离）验证 change
链路本身？后者能让底座建设期间系统仍在产出。
**倾向**：批 D 派工（现状模式）与底座 M0-M1 并行——批 D 的两个缺陷修复恰好也是
底座观测能力的补全（DR-17 就是事件旁路），一石二鸟。
