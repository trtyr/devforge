# Testing 阶段设计记录（2026-10-18 讨论）

> 来源：2026-10-18 17:47 用户口头设计 + 助手架构映射分析。本档是 P007 的设计真源；拍板项落 decisions/，未决项见 open-questions.md。

## 一、用户口径（设计 spec）

### 1. 测试内容

一整套**集成测试 + 端到端测试**等一系列测试方法（与 coding 阶段「只写单测、严禁 e2e」互补，两阶段测试组合不重叠）。

### 2. 测试架构

与前两阶段完全同构：**work Agent + review Agent**。之前怎么做，现在就怎么做。

### 3. 测试流程与输入

Coding 阶段完成后产出三产物：

- (a) 全部标记完成的 plan tree；
- (b) 仓库代码（已完成并通过 review）；
- (c) coding 阶段落地的文档。

**Testing Agent 不看代码**——看 plan tree 和项目文档（甚至只看文档）来写测试。看代码对它没有意义。

### 4. 可写度分级（文档的纯函数）

它不知道自己能写多少、也不知道理论上该写多少。按文档可写度分三种：

1. 完全一点测试都写不了；
2. 能写，但只能写一点；
3. 能写比较多，甚至全量。

分层级，但本质两套（二元关系）：**测试是否全面跟代码无关，纯粹跟文档有关**。它写完测试就开始跑。

### 5. 测试 Review 判据（对文档）

Review Agent 根据文档判断测试写得全不全、场景合不合理、覆盖面如何：

1. 能不能真正反映**业务关系**；
2. 能不能覆盖**用户场景**；
3. 能不能覆盖**极端用户面**。

### 6. 写不了测试的出口（移交链路）

1. **记录留痕**：直接阻塞并停掉测试阶段，在共享区域把「测试不了」记录留痕；
2. **移交 calling Agent**：将记录交给 calling 阶段的 calling agent；
3. **切换模式**：calling agent 进入「写文档模式」（而非编码模式），开始撰写文档；
4. **回到测试**：文档写完（一般不经 review，极端情况直接给）并 review 通过后，进入测试环节。

一般不会出现没文档的问题——前面的架构保证了文档足够详细。极端情况下 calling agent 写完文档不经 review，直接到测试 Agent；测试 Agent 拿新文档写测试 → 跑 → review 通过 → 测试阶段结束。

### 7. 用户结论

测试阶段跟前两个阶段没有太大区别；理解了前两个阶段，这个阶段概念上很好理解。

## 二、架构映射（助手分析：零新增概念）

| 设计要素 | 复用机制 |
| --- | --- |
| TESTING_SOP 注册 + planning→coding→testing 跨 SOP 链 | SopRegistry + start {sop} 触发（P004/P005 已落） |
| 黑板 testing/ 目录 | coding/ 布局同款（套件清单/todo/reports/blockers） |
| work + per-round fresh review | PlanningLoop/CodingSopLoop 同构状态机 |
| 取消/超时/失活收割 | run_with_watchdog + FNV 指纹（006 D002） |
| 双 profile（test-agent + test-review） | 渲染器 + 供给清单复用 |
| 提示词纪律反转 | coding「只单测禁 e2e」↔ testing「只集成/e2e 不单测」——组合互补本身是特性 |

**黑盒教义判定（成立）**：从文档长出来的测试验证「系统承诺了什么」而非「系统做了什么」——实现漂移一测现形；同时避免「照实现写测试把 bug 照抄进测试」。可测性是文档的纯函数，文档决定覆盖上限。

## 三、差距分析（需拍板的路由与边界）

1. **红灯归因**：测试跑挂只有两种可能——测试误读文档（修测试）或代码不符合文档（实现 bug，恰是本阶段最有价值产出）。测试 Agent 不看代码无归因能力，只能回读文档；对不上时「文档-代码分歧」入 blockers，此后回流 coding 修码还是 calling agent 裁决 → Q001。
2. **review FAIL 双根因**：除「完全写不了」外还有第四态——写完了但 review 判覆盖不够，根因是文档太薄，测试 Agent 重写无用。FAIL 应拆「测试写错 → 退回测试 Agent」与「文档撑不起覆盖 → 移交 calling agent」两路 → Q002。
3. **calling 阶段定位**：流水线第五环（串行 SOP）还是横切旁路服务？「写文档模式」是独立 SOP 还是模式位 → Q003。未审文档直接入测试的风险（文档自身 bug 获通行证）已声明，极端路径+留痕，可接受 → Q006。
4. **工程面**：测试代码进仓库 commit-on-pass（D009 同款，成为常驻回归资产）→ Q004；「不看代码」边界=允许读运行面（起服务方式/测试命令），禁读实现 → Q005；被测系统由测试 Agent 自起自跑自收。
5. **覆盖判定操作化**：review 产出「文档 ↔ 测试用例」追溯矩阵，覆盖面判断不玄学 → Q007。
6. **供给取舍**：测试 Agent 不看代码，codegraph（代码事实层）对其无意义甚至违纪；运行面是否保留 context7/web 待议 → Q008。

## 四、补遗（2026-10-18 17:56 第二轮讨论 + 业界侦察）

### 4.1 用户修正与澄濵

1. **「calling」系口误，实为 coding**：移交对象 = **coding agent**（写代码的那个），它进入「写文档模式」（而非编码模式）补文档后交回测试环节。→ 无新增阶段/Agent，原 Q003 消解；coding agent 本就看得见代码与文档。
2. **测试代码语言与落位**：测试用 **Python** 写，做端到端与集成测试，进仓库专门位置。
3. 用户自陈不熟测试领域，要求先上网侦察业界实践再定细节。

### 4.2 红灯分类学（回应「怎么定义测试跑挂」）

一条测试报 FAIL，只有三种成因：

| 类 | 成因 | 本质 | 去向 |
| --- | --- | --- | --- |
| A | 测试自身错（脚本 bug/环境没起/用例写歪） | 没测到任何东西 | 测试 Agent 修自己重跑（不需要看代码） |
| B | 被测系统行为与文档不符（断言失败） | **发现**——本阶段最有价值的产出 | 记中性「发现记录」（文档说 X/实测 Y/复现步骤）→ 移交 coding agent |
| C | 环境抖动（flaky） | 同一用例时绿时红 | 重跑去抖后再判（见 4.4） |

**归因权设计**：测试 Agent 不看代码 → 它没有归因权。B 类「是代码错还是文档错」由 **coding agent triage**——它看得见两侧，裁决改码（正常模式）还是改档（写文档模式）。测试侧只交中性发现+复现证据，不做归因。这统一了移交触发点：不只「写不了测试」，「测试发现文档可疑」也由 coding agent 裁决后走文档模式。

### 4.3 review FAIL 双根因（具体化）

- **根因①测试的错**：漏了文档明确写的场景 / 断言与文档矛盾 / 场景不合理 → 退回测试 Agent 重写（等价 coding 的 FAIL→fix 循环）。
- **根因②文档的错/薄**：测试本身写得好，但覆盖上不去——文档缺内容或有歧义，重写一百遍无用 → 移交 coding agent（写文档模式）补档 → 新文档回测试环节扩测试 → 重审。
- 与用户原「可写度三级」统一：写入时（完全写不了）与审查时（覆盖天花板）是同一机制的两次触发，本质都是文档不足回炉文档。

### 4.4 业界侦察（2026-10-18 web 检索）

**Doc2Test（ASE '26，2026-10-07 发表，工业界多 Agent 文档驱动 E2E 测试生成）**——与本设计同构的外部验证：需求分析 → 上下文感知 → 代码生成+自愈循环三阶段；90 次独立运行 94.4% 生成成功率、180 个注入回归检出 98.9%、token 比 zero-shot 单 prompt 省 86%；三个月 nightly Jenkins 运营，维护成本 −2.6 人日/sprint，flaky 率 11.4%→4.6%。可借鉴：① 阶段分离（分析/感知/生成/自愈）对应我们「读文档→写→跑→审」；② **flaky 是真实痛点**，需重跑去抖机制（同一用例失败先重跑 N 次再判红，防环境抖动污染 B 类归因）。

**Python 测试套件布局惯例**（IBM/mcp-context-forge tests/AGENTS.md、relaydeck TESTING.md 等）：仓库根 `tests/` 下 `unit/ integration/ e2e/` 三层分目录 + pytest marker 分层；**tests/AGENTS.md**（给 AI 助手看的测试约定文档）惯例直接可抄；HTTP 黑盒用 httpx/requests。与本项目咬合：coding 阶段已定「只写单测禁 e2e」→ coding 写 `tests/unit/`，testing 阶段写 `tests/integration/ + tests/e2e/`，同树不打架。
